# dct 控制层：看 → 判断 → 动手

日期：2026-09-26
状态：总设计，待用户审阅。三块具体的东西（摄像头、屏幕和键鼠、软件连接器）各自另有设计和计划
关联：`2026-09-26-dct-judge-design.md`（判断引擎）；`~/work/dc/dc-vault/docs/superpowers/specs/2026-09-26-dc-vault-design.md`（记忆）；
`~/work/dc/dc_desktop/docs/superpowers/specs/2026-08-06-platform-connectors-design.md`（dc_desktop 的连接器，本设计要与它对齐）

## 要解决什么

用户的原话：「我想 dct 来控制其他软件」「我本身就想带 dc_desktop 那样的连接器」「我想 dct 能帮我打游戏」
「dct 能够帮我连接外部设备，比如说连我的摄像头」「dct 用来控制，dcv 用来记忆」。先做哪个？「都做」「这个必须都要做」。
补充：「我有 esp32 的摄像头」「键盘，屏幕，鼠标。如果能连手机就更好」。

这些要求底下是同一个循环：

```
   看                      判断                         动手
 连接器读进来 ──────▶  judge（+ dcv 里的规则）──────▶  连接器执行（先过分档把关）
 事件 / 画面 / 截屏      选哪个、打几分、是不是          发消息 / 按键 / 点击 / 开关设备
```

- **dct 管控制**：连接器、循环、把关。
- **dcv 管记忆**：你的偏好和规则（`rule` 只能你亲手写或来自你亲自拍板，见 dcv 设计）。
- **judge 管判断**：Jev 格式的「选哪个、打几分、是不是」，能看图。

## 讨论中已经定下的事（不在本设计里再议）

- **dct 去连别人，不让别人来连 dct。** 别的软件不会为 dct 改自己，所以 dct 主动用它们已经开好的门。
- **dct 自己带连接器**（用户明确要求），像 dc_desktop 那样。
- **三类都做，而且必须都做**：软件、屏幕和键鼠（电脑和手机）、设备。下面的「先后顺序」只是排队，不是取舍。
- **动作分档**，与 dc_desktop 连接器设计的 `read / content / money` 对齐（见下）。
- **判断用 judge**，模型走 DC 网关的 Qwen3-VL。

## 三类连接器

| 类别 | 看 | 动手 | 第一批 |
|---|---|---|---|
| **设备** | 摄像头画面（之后：麦克风、传感器） | 之后：ESP32 的屏幕、喇叭、串口 | **ESP32 摄像头**（经 Wi-Fi），然后是 Mac 自带摄像头 |
| **屏幕和键鼠** | 截屏（电脑整屏或某个窗口；手机屏幕） | 模拟键盘、鼠标；手机上的点按、滑动、打字 | 电脑：回合制 / 棋牌 / 慢节奏游戏；手机：安卓 |
| **软件** | 收消息、读数据 | 发消息、建日程、点按钮 | Mac 自带 App（AppleScript）、Laya（MCP）、飞书（官方接口） |
| （软件，浏览器那一路） | 读网页 | 在网页上操作 | 抖音 / 小红书 / 淘宝——与 dc_desktop 的浏览器能力宿主对齐后再做 |

**屏幕和键鼠这一类的意义比打游戏大**：能看屏幕、能按键盘，就能操作任何有界面、却没有开放接口的软件。

### ESP32 摄像头

dc_desktop 2026-08-10 的实测记录里，ESP32-S3 板上已经跑过一个 Wi-Fi 控制服务（开机自启的 `/main.py`，
`GET /status`、`POST /exec`，都要 `X-Token`；凭据在板上 `/wifi.json`），摄像头固件用的是
cnadler86/micropython-camera-API（MicroPython 1.27，S3 八线 PSRAM 版）。所以接法是：

- 在板上的服务里加一个 `GET /capture`，拍一张、直接回 JPEG；dct 用普通 HTTP 按间隔去取。
  **不需要 macOS 的摄像头权限，也不用装 ffmpeg**——比 Mac 自带摄像头还简单，所以排在它前面。
- ⚠️ 明文 HTTP：token 和画面在同一个 Wi-Fi 里抓包看得见。家里的网络可以接受；画面是你房间的样子，这一点要你知道。
- ⚠️ 当时那两块 KIDVIEDU 板的**摄像头模组都没通电**，用户打算另买 Aideepen ESP32-S3-CAM（OV3660）。
  **现在手上这块能不能出画面，是摄像头那一步的第一个问题**：能，就直接接；不能，先把板子调通。
- 板子本身也是个设备：以后它的屏幕、喇叭可以当 dct 的「动手」那一端（显示状态、说一句话）。

### 手机

- **安卓：能做。** 用 `adb`（USB 或同一 Wi-Fi）：`adb exec-out screencap -p` 截屏，`adb shell input tap / swipe / text / keyevent`
  点按、滑动、打字。一次性要做的准备：手机上打开「开发者选项」里的 USB 调试，第一次连电脑时在手机上点「允许」。
- **iPhone：难得多。** 苹果没有对应的开放通道，要装 Xcode、给手机装一个自己签名的测试程序（WebDriverAgent）
  才能截屏和点按，而且签名每周可能要续。先做安卓，iPhone 单独评估值不值得。
- 注意方向：dct 现有的「手机端」是**手机看 dct**；这里是 **dct 操作手机**，两件事。

## 连接器规范（所有连接器讲同一种话）

每个连接器是一份**声明**加一段**实现**：

```toml
id = "camera"
kind = "device"            # device | screen | app
label = { zh = "摄像头", en = "Camera" }

[[sense]]                  # 能看什么
name = "frame"
produces = "image"         # image | event | text

[[action]]                 # 能做什么，每个动作标好一档
name = "send_message"
tier = "content"           # read | self | content | money
params = { to = "string", text = "string" }
```

- **收进来的统一成事件**：`{connector, sense, time, text?, image?, meta}`，学 Laya 的统一事件格式。
- **发出去的统一成动作**：`{connector, action, params}`，执行前必须过把关（下一节）。
- **实现有四种后端**，连接器自己选：内置（Rust 写在 dct 里）、命令行（调系统自带工具，如 `screencapture`、
  `osascript`）、MCP（dct 当客户端，连别人现成的 MCP 服务，如 Laya）、浏览器（与 dc_desktop 的能力宿主对齐）。
- **与 dc_desktop 共用格式**：一个平台的站点知识只写一次，dct 和 dc_desktop 都能用。两边的格式具体怎么合，
  是「软件连接器」那份设计的第一件事。

## 分档把关

| 档 | 含义 | 例子 | dct 怎么做 |
|---|---|---|---|
| `read` | 只看，不改变任何东西 | 摄像头一帧、截屏、读邮件 | 直接做 |
| `self` | 撤不回，但只影响你自己 | 建一条备忘录、加自己的日程、单机游戏里按键 | 直接做，事后在看板/Telegram 上告诉你 |
| `content` | 对外：别人会看到 | 发消息、发邮件、发帖、网络游戏里的公开动作 | **每次先问你**，除非 dcv 里有一条你亲手写的 `rule` 放行这一类 |
| `money` | 动钱 | 下单、改价、改库存、充值、游戏内购 | **每次都问，永不自动**，规则也不能放行（与 dc_desktop 一致）；执行要幂等、可预演、有记录 |

- 能撤回的改动（项目里的文件）不在这张表里：它们照旧由快照兜底、直接做。
- 「先问你」走现成的路：看板上一行提示，或者 Telegram 推一条，你回一个字。
- 每一次 `self` / `content` / `money` 动作都记进 journal（`src/journal.rs` 已有），谁、什么时候、做了什么、谁批的。
- **放行规则只认 dcv 里 `source` 是 `manual` 或 `decision` 的 `rule`**：导入的、agent 写的、连接器读进来的内容，
  都不能给自己放行（提示注入的防线，dcv 设计里已经定了）。

### 连接器之外的直接操作怎么办

dct 里跑的 agent 开着「跳过权限确认」，它可以不经过连接器，直接 `osascript` 发邮件——今天就是这样
（2026-09-26 的备忘录演示，dct 一声没吭）。所以把关要有第二道：

- **Claude Code（以及借它跑的 Kimi / GLM / DeepSeek / Qwen API）**：dct 给会话装一个 PreToolUse 钩子，
  agent 每次执行命令前先问 dct；dct 用 judge 判断这条命令属于哪一档，按上表处理。
  **待实测**：在跳过权限确认的模式下，钩子还会不会执行、说「不行」时拦不拦得住。
- **Codex / qwen / opencode**：有没有同类钩子待查。**没有钩子的 agent，会话里不给开任何连接器。**

## 授权：默认全关

- 每个连接器**默认关着**，要你在设置页里亲手打开一次（与 dc_workbench「默认全拒」同一原则）。
- 摄像头、截屏、键鼠这三样**开着的时候，屏幕上一直有一行关不掉的提示**（「摄像头在看」「dct 在操作键鼠」），
  跟直播那行「正在直播」一个道理：危险的不是功能本身，是忘了它开着。
- **键鼠有一个急停键**：dct 在操作键鼠时，你一动真实的鼠标或按任意键，它就停下，等你说继续。
  操作手机时同理：你一碰手机屏幕（`adb shell getevent` 能看到真实触摸），它就停。
- macOS 的系统授权（摄像头、屏幕录制、辅助功能）第一次用时系统会弹窗；dct 在弹窗之前先用一句话说明为什么要它，
  跟手机端「防火墙会问你」那条做法一样。

## 跑在哪儿

- **「看」的循环跑在守护进程里**：摄像头每隔几秒一帧、定时查收消息，这些要在你关掉界面之后照样跑——
  守护进程才是产品本体。这要改协议（加「开关一个连接器」「连接器事件」两类请求），协议版本加一。
- **agent 通过 `dct mcp` 用连接器**：dct 开一个 MCP 服务，把已经打开的连接器的动作列成工具。agent 调用时同样过把关。
- **dct 自己的循环**（「看到 X 就做 Y」，比如「有人进房间就把会话暂停」）直接调连接器和 judge，不经过 agent。
  这种循环怎么写、存在哪（很可能是 dcv 里的一类知识），在摄像头那份设计里定。

## 先后顺序

每一步单独设计、单独计划、单独能用：

0. **judge**（已设计）：先跑 `dct judge --probe`，验证网关给不给概率。**拿不到网关密钥，后面全部停在这一步。**
1. **底座**：连接器规范、分档把关、授权开关、提示行、journal 记录、`dct mcp` 骨架、协议加一。
   同时实测 Claude Code 钩子。
2. **摄像头**：只读。先 ESP32（Wi-Fi 取帧），再 Mac 自带摄像头。拍帧 → judge → 事件；第一个「看到 X 就做 Y」的循环。
3. **屏幕和键鼠**：电脑截屏 + 模拟键鼠 + 急停；然后安卓手机（adb）。第一个游戏选一个回合制的单机游戏
   （或者有官方接口的，如 lichess 下棋）。
4. **软件连接器（接口那一路）**：Mac 自带 App、Laya（MCP）、飞书。先定与 dc_desktop 共用的格式。
5. **软件连接器（浏览器那一路）**：抖音 / 小红书 / 淘宝，与 dc_desktop 的浏览器能力宿主对齐。

## 已知的限制（不是写得好不好能解决的）

- **速度**：一次判断走一次网关请求，秒级。摄像头只能「几秒看一次」，游戏只能做回合制和慢节奏的；
  射击、格斗这类实时游戏做不了。要快，得在本机跑小模型——那是另一件事。
- **网络游戏的封号风险**：很多网游禁止脚本，反作弊会封号。第一个游戏选单机的；网游由你自己决定、自己承担。
- **隐私**：摄像头和截屏画面会发到你自己的 DC 网关服务器上。默认关、开着有提示，就是为了这一条。
- **平台**：先做 macOS（你的机器）。摄像头、截屏、键鼠在 Windows 和 Linux 上都要各写一份，之后再说。

## 还没定、在各自的设计里回答

- ESP32 那块板现在能不能出画面（见上）。
- 你的手机是安卓还是 iPhone。
- Mac 自带摄像头怎么拍：macOS 没有自带的拍照命令行工具。候选：调 `ffmpeg`（dct 像装 git 那样帮你装一份）、
  或者直接调系统框架（不引 C 代码的前提下）。摄像头那份设计里实测后定。
- 模拟键鼠用系统自带的 `osascript`（System Events）还是直接调系统事件接口，屏幕那份设计里定。
- dct 和 dc_desktop 的连接器格式怎么合成一份，软件连接器那份设计里定。
