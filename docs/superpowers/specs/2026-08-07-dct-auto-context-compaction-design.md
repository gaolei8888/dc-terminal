# dct 自动上下文压缩 —— 设计

**状态：** 设计已定，未实现。一个开放取舍待用户拍板（见「未定的一件事」）。
**关系：** `2026-08-06-dct-supervisor-vision.md` 第 4 件事（摘要）的近邻，但不是同一件。
复用已合并的 LLM 连接层（`2026-08-06-dct-llm-connection-design.md`）。

## 要解决什么

用户的原话：**「如果 dct 发现对话 context 过大了，可以自动提示用户进行 context 压缩，
并且能自动恢复到压缩前的断点。」** 追问「断点指什么」时他三个都选了——agent 在干的
那件事、压缩前的屏幕内容、打到一半的输入——并给了落点：

> 就是达到一个不影响用户当前会话的地步。

所以这件事的验收标准不是「能压缩」，是**压缩这件事不打扰人**。提示要弹（用户做主），
但一旦点头，后面全程 dct 自己扛。

## 推翻了什么

2026-08-04 那轮调研的结论是「**先做手动键、不要自动检测**」，理由两条：

1. 当时凭印象写的 `Context left until auto-compact: (\d+)%` **从没验证过**，
   新起的 claude 会话根本不显示余量；
2. Claude Code 自己会自动压缩，dct 再压一层多半是重复劳动。

第 1 条今天仍然成立，本设计不靠它（见下）。第 2 条被用户的实际诉求推翻了：
他要的不是「压缩」这个动作本身，是**压缩之后不用重新解释一遍**。
Claude Code 自动压完照样会丢掉「我们刚才在干嘛」，那正是痛点所在。

## 一、触发信号

### 主信号：dct 自己数字节

每个字节都过 dct 的 PTY，它天然知道发进去多少、吐出来多少。不依赖任何厂商文案，
换 agent、换版本都不会坏。

**但它脏，这一点必须写在前面。** Claude Code 跑在备用屏上（实测 `?1049h`），
每敲一个字符都重画整屏，PTY 吐出来的字节里绝大部分是重绘，不是对话增长。
所以字节数跟「上下文有多满」只是**单调相关，不成比例**。

后果：阈值**不能凭空定，必须一个 agent 实测标定一次**——跑一个真实会话直到它自己
触发自动压缩，记下那一刻的计数器读数，取八成写进 profile。

```toml
# profiles/claude.toml
compact_command  = "/compact"
compact_at_bytes = 12_000_000   # 实测标定；这个数字是编的，用前必须真跑一次
```

**两个字段都写了，功能才对该 agent 打开；缺任何一个 = 关着。** 不猜、不给默认值。

这条规矩照抄 `Profile::error_pattern` 的注释，那里已经把教训写死了：

> 只给见过真实错误文案的 profile 写。凭想象编正则会造出误报，而误报比不报更糟。

这里误报的代价是白白烧掉一次压缩，并且打断用户——比不报更糟，同一个道理。

计数器住在 `Session` 里，只加不减，压缩成功后归零。

### 备用信号：以后实测到的屏幕提示串

哪天真在屏幕上实测到稳定的余量提示，加 `context_pattern` 字段，
**优先于字节计数**——真信号永远压过代理指标。字节计数留给没有提示串的 agent 兜底。
两条信号并存，不是二选一。

**注意：** 用户机器上见过的 `ctx:56%` 是他自己配的 statusLine，不是 Claude Code 自带的，
不能当信号用。

## 二、提示与用户做主

到阈值时**不自动压**，先问。提示走会话底栏，跟滚屏提示同一条，`message` 优先的规矩照旧。

文案走 `i18n::msg`，中英各一份，不带黑话（不出现「上下文」「token」「compact」）：

> 这个会话攒的东西快到上限了。现在整理一下？整理时你不用管，完事会自动接着刚才的活。
> （y 整理 / 回车先不管）

两条「不打扰」的约束：

- **用户正在打字时不弹。** 输入框里有半截内容就往后压，等他敲完回车再说。
- **拒绝一次就闭嘴一阵。** 不能每帧问一次；再攒一截才允许问第二次。

## 三、点头之后的四步

1. **存。** 用户输入框里那半截字存起来。屏幕历史本来就在滚屏缓冲里（2000 行，
   `2026-08-04-dct-scrollback-design.md`），不用另存。
2. **写交接条。** 把最近的会话历史交给 dct 自己的模型，写一段「刚才在做什么、
   做到哪、下一步」。**这一步有超时**；写不出来、或者根本没配 `[llm]`，退到第 2 条路
   （把最后 N 行原样存成文件，压缩后告诉 agent 去读）。缺 LLM 不等于功能不可用。
3. **压。** 把 `compact_command` 敲进去，然后等。压缩跑完没有，靠现有的
   `busy_pattern` / `idle_pattern` 判断——不新造状态机。
4. **接回去。** 交接条送进 agent，那半截输入还回输入框。

全程会话状态显示为「整理中」，既不是空闲也不是卡住。看板上必须看得出来它在忙什么，
否则用户会以为会话挂了。

### 为什么是 LLM 写交接条，不是机械搬运

比过三个路子：

| | 做法 | 结论 |
|---|---|---|
| A | dct 的 LLM 写一段交接条，压缩后自动送回 | **选它。** 只有它能兑现「接着干」，而 LLM 层是现成的，这轮不用再造 |
| B | 存文件，让 agent 自己去读 | 不依赖模型、可预测，但 agent 要多花一轮去读，且未必接得上。**降级路径，不是备选** |
| C | 什么都不注入，靠 agent 自己的压缩摘要 | 最省，但压完 agent 大概率问「我们刚才在干嘛」——正是要消灭的那一幕 |

A 在没配 LLM 时自动退化成 B。

## 四、失败怎么办

用户不是程序员，每一句他看得见的话都要说清下一步干什么。

| 出了什么事 | 用户看到 | dct 做什么 |
|---|---|---|
| 交接条写不出来（超时/LLM 没配/调用失败） | 不提这件事 | 静默退到 B，流程照走 |
| 敲了 `compact_command` 但 agent 没反应（超时） | 「整理没成功，会话还是原样，你可以接着用。」 | 计数器**不归零**，退避后可再问 |
| 压缩中会话死了 | 走现有的会话失败解释路径 | 不新造一套 |
| 半截输入还不回去 | 「你刚才打的字在这里：……」显示出来让他自己贴 | 宁可让他复制，也不能吞掉 |

**计数器只在确认压缩成功后归零。** 失败还归零等于把功能关到下一个周期，
而用户的上下文其实还是满的。

## 五、明确不做

- **不自动压缩，永远先问。** 用户是这个会话的主人，替他做主一次就够他不再信任这个功能。
- **九宫格里不弹提示。** 那是只读平铺视图，弹一个要按 y 的提示没地方按。
- **不做跨会话的上下文管理、不做摘要归档。** 那是 supervisor vision 第 4、5 件事。
- **不猜 `compact_command`。** 每个 agent 的压缩命令得实际验证过才写进 profile。

## 六、怎么测

- **纯函数**：到没到阈值、该不该弹（打字中/退避中）、退避怎么涨、失败后计数器不归零。
  这些不碰 PTY、不碰网络，全部可单测。
- **假 agent**：仓库已有起 `/bin/sh` 当会话的测试夹具。用它验证「敲了命令 → 状态变整理中
  → 完事状态回来 → 计数器归零」，以及超时路径。
- **交接条不测内容质量**，只测「LLM 不可用时确实走了 B」和「超时确实会超时」。
  模型写得好不好不是自动化测试能断言的事。
- **不测的**：真实 agent 上阈值准不准。那要靠标定，是人工的事，写进 profile 注释里。

## 未定的一件事

第一段那个取舍用户还没拍板：

> 这功能做完之后，**每个想用的 agent 都得先跑一次长会话来标定阈值**，否则它对谁都不开。

三个选择：
1. 接受。功能做完先只对标定过的 agent 开（大概率先只有 claude）。
2. 先做标定工具——dct 加一条命令，把当前会话的计数器读数打出来，让标定变成一句话的事。
3. 先不管准不准，给个保守的默认值。**不推荐**，理由见第一段。

动手之前要先定这个。
