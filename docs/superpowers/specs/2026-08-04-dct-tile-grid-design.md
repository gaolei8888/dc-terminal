# dct 看板九宫格设计

日期：2026-08-04
状态：设计已确认，待实施

## 要解决的是什么

看板今天是一张列表，每个会话只有一行元信息加一行 `activity` 文本
（`src/pty.rs:203` 的 `last_line()`，最后一个非空行）。同时看着三个 agent
干活的时候，这一行不够：想知道每个 agent 正在输出什么，只能挨个 `Enter`
进去再 `Ctrl+Q` 出来。

要的是一眼看到所有会话的**实时画面**：平铺成格子，每格是一个会话屏幕的
活的切片，最多九格一屏。

## 两个已经做掉的决定

### 格子只读，交互靠放大（zoom-to-type）

考虑过让焦点格直接收键盘输入（tmux 面板那种）。问题卡在
`src/pty.rs:124`：PTY 和 vt100 parser 一个会话只有一份尺寸，全局共享。
格子大约 38×11，要打字就得把会话缩到这个尺寸——agent 在 38 列下惨不忍睹，
纯 shell 收到 SIGWINCH 又不重绘（vt100 是裁剪不是回流），画面直接残掉；
另一个已附加的客户端还会被连带拽小。

所以：**格子里任何按键都不会转发给 agent。** 想交互，`Enter` 放大——
放大就是现有的附加视图，全宽全键盘，一个键的距离。省掉整套按键分流，
换来的是每次交互都是完整屏幕而不是 38 列的窗缝。

### 九宫格是第二视图，不取代列表

列表在会话超过九个、要看完整项目路径的时候仍然更好用。九宫格用 `g`
从看板切过去，`g` 或 `Ctrl+Q` 切回来（`Ctrl+Q` 退一层的房规不变）。
哪天九宫格证明了自己是日常主力，再翻默认，翻的成本是一行。

## 布局

格数自适应，上限九：

| 会话数 | 布局 |
|---|---|
| 1 | 整屏一格 |
| 2 | 1×2 |
| 3–4 | 2×2 |
| 5–6 | 2×3 |
| 7–9 | 3×3 |

超过九个翻页：焦点移出边缘自动翻到下一页，角落画页码 `2/3`。

每格一行标题（agent 名、状态色、会话号）加画面区，焦点格边框高亮。

画面区是会话 120 列屏幕的**只读切片**：行数取格子画面区能装下多少
就要底部多少行（agent 的输入框和最新输出都在底部），列从左对齐截断，
带样式的 span 原样画，不画光标——只读的格子画光标只会误导人去打字。
九宫格**永远不发 `Request::Resize`**——会话尺寸归附加视图管。

## 数据怎么来

现有 `Request::Screen` 一次只问一个会话，而 `src/client.rs` 的连接是
一问一答串行的，九个格子九个来回没有必要。加一对批量消息：

```rust
Request::Screens { ids: Vec<u64> },
Response::Screens { screens: Vec<ScreenEntry> },  // id、lines；不带光标，格子用不上
```

纯增量改动，按滚屏设计 0.1 节的规则**不加协议版本号**。只请求当前页
可见的会话，300ms 一轮——看板本来就是 150ms 的轮询节奏，九宫格比它更松。
列表视图的请求路径一字不动。

## 按键

| 键 | |
|---|---|
| 方向键 | 移动焦点 |
| `Enter` | 放大 = 现有附加视图 |
| `s` `u` `d` | 对焦点格生效，语义同列表 |
| `n` `N` `p` `c` `q` | 不变 |
| `g` / `Ctrl+Q` | 回列表 |

## 边界

- 会话停了：格子留着，标题变灰，画面冻在最后一帧——和列表的行为一致。
- 新界面对老守护进程：`Screens` 不认识，回 `Response::Error`。九宫格里
  按格显示「后台服务需要重启：`dct restart`」，列表视图照常能用。
- 终端太小（约小于 60×20）：显示「窗口太小，放大终端窗口后再试」，
  不画残格子。

## 先决条件与落点

滚屏设计 0.2 节的 `ui.rs` 拆分先行。九宫格落在 `src/ui/grid.rs`，
是 `board.rs` 的兄弟模块。拆分完成前不动手，省得往 4000 行的文件里
再塞一个视图。

## 怎么验证

- 单测：布局数学（会话数 → 格子形状、翻页边界）、切片数学（底部 N 行、
  列截断不劈开宽字符）。
- 集成：对真守护进程开两三个 shell 会话，`Screens` 批量请求回来的
  样式 span 和 id 对得上号。
- `ui.rs` 拆分那一步的 172 个测试数量守恒，按滚屏设计的规矩来。
