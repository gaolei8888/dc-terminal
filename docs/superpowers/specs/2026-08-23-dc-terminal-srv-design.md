# dc-terminal-srv：手机当客户端 —— 设计

**状态：** 待实现
**起因：** 2026-08-23 用户指出：**中国大陆没有 Telegram 可用**，`2026-08-10-dct-phone-channel-design.md`
落地的那条通道在国内是死的。先后否掉了「短信当客户端」和「手机直连笔记本」两条路（见「问题」），
定下来做一个自己的中转服务 `dc-terminal-srv`，**只服务 dc_classroom 上注册的用户**。
**关联：** `2026-08-10-dct-phone-channel-design.md` —— 那一版仍然成立，但角色变了：
**它是「推送」，本设计是「客户端」**。两者不重叠，见「和手机通道的分工」。

---

## 问题

会话跑在用户自己的笔记本上，人却常常不在电脑前。要让手机成为一个真的客户端（看画面、回话、批准、
打断），唯一的技术障碍是**手机够不到那台笔记本**：家用宽带在运营商 NAT 后面，没有公网地址。

三条路，都试过，都不行：

**局域网直连。** daemon 起一个本地 HTTP server，手机连同一个 WiFi 就能打开。零依赖、零费用、
数据不出门——但**出了门就没了**，而"人不在电脑前"恰恰多半意味着人不在这个 WiFi 里。它解决的是
"我在沙发上"，不是"我在地铁上"。

**内网穿透（frp / cloudflared）。** 技术上可行，但目标用户是 dc_classroom 的学员，
`dc_classroom/CLAUDE.md` 第一条写着「**学生不是程序员**」。让他们配一个隧道、开一个端口、
理解什么是回调地址，等于把这个功能只发给已经不需要它的人。

**短信当客户端。** 监管形状决定了它做不成客户端，不是技术问题：

- **出站必须走模板。** 阿里云/腾讯云短信要求签名 + 预先报备的模板，只能往变量槽位里填字，
  审核明确拒绝会话式内容和 URL。dct 的推送是自由文本（「3 号「修登录白屏」干完停下来了」），
  塞进模板之后只剩「您的会话 ${id} 已完成」——名字、原因、合并成一条的那几件事全丢了。
- **入站要上行短信。** 106 号段开上行是单独的资质和费用，个人开发者基本拿不到，延迟也不稳。
  而"收到推送直接回一句话敲进会话"正是手机通道一半的意义。
- **没有消息身份。** 短信没有「回复某一条」的概念，`bridge.rs` 现在靠 `outbound_map`
  做的「长按回复 → 自动路由到那个会话」整套没了，只能退回 `/use N`。
- 中文 70 字一条，合并推送会被拆成多条计费。

**结论：短信只能是最后一档降级告警**（一句「dct 有事找你」），不能是客户端。

## 形状

```
用户的笔记本                  dc-terminal-srv               用户的手机
┌───────────────┐            ┌──────────────┐          ┌──────────────┐
│ dct daemon    │─出网长连接─▶│  信封路由     │◀──HTTPS──│ 手机网页      │
│ PTY / 会话     │            │  账号鉴权     │          │ 同一个账号登录 │
└───────────────┘            │  配额限流     │          └──────────────┘
                             └──────┬───────┘
                                    │ 「这个 token 是谁」
                                    ▼
                             dc_classroom（账号 / Redis）
```

**笔记本主动出网**，所以不需要公网地址、不需要端口映射、不需要学生碰路由器。这是这个方案存在的
全部理由——上面三条路都是卡在这一点上。

---

## 决定一：srv 不解析 dct 协议，只转发信封

`proto.rs` 里那套 `Request`/`Response` 原样复用，**手机网页就是一个远程的 dct 客户端**。
srv 看到的是一个信封：`{from, to, seq, payload}`，`payload` 对它是不透明字节。

理由不只是省事：

- **srv 永远不会成为版本瓶颈。** `PROTOCOL_VERSION` 每升一次都要求所有解析方跟着改；srv 不解析，
  就不用跟。手机网页和 daemon 之间那份契约由 `proto.rs` 自己的守卫测试钉着
  （`the_request_shape_is_pinned_to_the_protocol_version`），不需要第二份。
- **它和端到端加密是同一件事的两面**（见决定二）：srv 本来就不该看得懂 payload。

**推论（写死）：任何"服务端要看一眼内容才能做"的功能都不做。** 服务端渲染、会话回放、
内容审计、关键词告警——全部出局。要它们就得放弃加密，那是另一个产品。

---

## 决定二：端到端加密，srv 只知道「谁连了谁、多少字节」

**威胁模型说清楚：终端画面就是学员的源代码**，还包括他们往 agent 里敲的一切——粘进去的 API key、
数据库连接串、客户资料。这是一台**你们运营的**服务器，一旦明文，任何一次服务端事故（日志落盘、
备份泄露、内部越权）都是「学员代码泄露」，而受害者没有任何办法自保。

所以 srv 转发的是密文。它能看到的只有：哪个账号、哪台设备、什么时候、多少字节。

**密钥怎么来——支点是二维码，那是唯一不经过服务器的信道。**

1. 用户在 dct 里开「手机」设置页，daemon 生成一对 X25519 密钥，把**公钥 + 一次性配对码**
   画成二维码显示在终端里。
2. 手机（已经用 dc_classroom 账号登录）扫码，生成自己的密钥对，用 daemon 的公钥算出共享密钥
   （X25519 ECDH → HKDF），把自己的公钥经 srv 回传。
3. 之后双向都是 ChaCha20-Poly1305 加密的信封。**srv 全程只见过两个公钥，算不出共享密钥。**

**代价，明明白白写在这里：**

- **必须当面扫一次码。** 手机不在电脑旁边就配不上——不给「用邮箱收一个链接」这种后门，
  那等于把密钥交给服务器，整个模型就塌了。
- **服务端排障只有元数据。** 用户报「手机上画面卡住」，你们能看到的是连接状态、字节数、
  最后一次心跳，看不到内容。这是设计的一部分，不是缺陷。
- **换手机 = 重新配对。** 旧设备在设备列表里撤销。

**教学审计怎么办（老师要看学生屏幕）？** 这个需求几乎一定会来，而它和 E2E 直接冲突。
**不要靠"服务端反正能看到"来实现它**——正确做法是多收件人信封：学生的 daemon 在本地
**额外用老师的公钥加密一份**，老师端自己解。这样"谁能看"是学生机器上的一个明确开关，
而不是服务器的默认能力。这一条不在第一期，但协议里要留出 `recipients: Vec<PubKey>` 的位置，
免得将来只能靠"把加密关掉"来满足它。

## 决定三：身份接 dc_classroom，一个账号多台设备

不重建用户体系。srv 拿到 token 之后问 dc_classroom「这是谁」（REST 接口，或共享 Redis 里的
会话），拿回一个用户 id。

- **笔记本侧**：token 存 `~/.dct/secrets.toml`——那个文件已经是 0600 / Windows 单条 ACL
  （`src/secrets.rs`），不用新开一处存密码的地方。
- **一个账号 N 台机器**：设备有名字（主机名）和最后在线时间，手机上选择连哪一台。
- **撤销**：设备列表里能踢掉任何一台；被踢的 daemon 下一次心跳收到拒绝，本地 token 作废。
- **学员不是程序员**：整个配对流程在 dct 里是「设置 → 手机 → 扫这个码」，在手机上是
  「登录 → 扫码 → 出现你的电脑」。没有第三步。

---

## 决定四：手机是完整终端，但**没有 resize 权**

用户明确要「完整终端」而不是「看一眼 + 回一句」。可以做，但有一条硬约束必须先摆平：

**PTY 只有一个尺寸。** 手机竖屏约 40 列，笔记本 120 列。如果两个客户端都能发
`Request::Resize`，agent 的 TUI 会在两个宽度之间来回重排——桌面那边的画面会因为你在地铁上
掏出手机而抖动，而且 Claude Code 这类 TUI 重排是有代价的（历史会被重新折行）。

**规则：桌面 dct 是唯一有权 `Resize` 的客户端。手机看的是同一块画布**，
缩放和平移在手机端做（画面是结构化的 spans，不是图片，缩放是 CSS 的事）。
放弃"手机上自动重排"这一条之后，"完整终端"其余部分都能做实：

- **虚拟键行**：`Esc` `Tab` `↑` `↓` `←` `→` `Ctrl` 常驻在软键盘上方一行。
  这些键手机键盘上没有，而 agent 全都要用（Esc 关弹窗、Tab 切模式、方向键选菜单、Ctrl+C 打断）。
- **输入法**：中文输入靠 composition 事件，**组合期间一个字节都不能往上送**——
  逐字符转发会把拼音本身敲进 agent。
- **滚回历史**：走现有的 `Request::Scroll`，跟桌面同一条路。
- **`F2`…`F6` 这些 dct 自己的键不出现在手机上**：它们是终端 UI 的逃生键，手机上有自己的返回。

## agent 跑在哪里：本机，而且笔记本得醒着

**agent 跑在用户自己的笔记本上，跟现在完全一样。** 手机上不跑任何东西，srv 上也不跑。
手机敲的字经 srv 解密之后写进那个会话的 PTY——跟用户在自己键盘上敲是同一个入口
（`Request::Input`），agent 不知道有手机这回事。文件、git 快照、`u` 撤销、
`secrets.toml` 里的 API key，全部留在本机。

**代价：笔记本得醒着。** dct 一直说的「关掉终端窗口，会话照跑」指的是关**窗口**，
不是合**盖子**——合盖休眠之后进程被冻住，agent 停在半路，而"人在外面、电脑在家"
恰恰是最想用手机的场景。三条应对，前两条属于本设计范围：

1. **说清楚**（第一期）：手机端发现心跳停了，明说「你的电脑睡着了」，而不是转圈。
   这是「错误必须告诉用户下一步做什么」那条房规在这里的落点。
2. **有会话在干活时不让机器睡**：daemon 在任一会话处于 `Working` 时申请
   （macOS `caffeinate` / Windows `SetThreadExecutionState`），全空闲就放开。
   这一条属于 dct 本体，跟 srv 无关，但没有它上面那句提示会天天出现。
3. **让 agent 根本不跑在笔记本上**——`dc_classroom/CLAUDE.md` 里那个 `dc_workspace`
   容器集群就是执行层。同一个 daemon 跑在容器里，手机连的「设备」从「我的笔记本」
   变成「我的云工作区」，**协议一行都不用改**：对 srv 来说两者都只是一个出网连上来的设备。

**第 3 条要在界面上跟第 1 条分清楚。** agent 跑在你们的容器里时，端到端加密只保护
「传输和中转」，保护不了「执行主机」——代码本来就在那台机器上。两种设备的隐私承诺不一样，
设备列表里必须写明白是「我的电脑」还是「云工作区」，不能让用户以为它们是一回事。

## 流控：16ms 一帧的东西不能直接上公网

桌面附加视图 16ms 拉一帧（`src/ui/mod.rs` 的循环），那是本地 socket 的节奏。上了公网要改：

- **手机端 300ms 拉一次**，且**只在页面处于前台时拉**（`visibilitychange`）。
  锁屏之后一帧都不该走。
- **只传变化的行**。`Response::Screen` 现在是整屏 spans；同一块画布上多数帧只改几行，
  差量传输是第一期就要做的，不是优化——它直接决定了流量账单。
- **按账号配额**：设备数、并发连接数、每日字节数。超了给明确的话（「今天的额度用完了」），
  不是静默断开。

## 断线：心跳要短于运营商 NAT 超时

家用宽带和 4G 的 NAT 映射通常 60–120 秒不活动就回收。**心跳间隔定 45 秒**，
daemon 侧断线自动重连（指数退避，跟 `client.rs` 现有的重连约定同形）。
手机侧断线要**看得出来**——沿用桌面那套：连接断了整条标题栏变红，写明"画面可能已过期"。

## 和手机通道（Telegram）的分工

两者不重叠，都要留着：

| | 负责 | 网页关着的时候 |
|---|---|---|
| **手机通道**（`bridge.rs`） | 「有事找你」——干完了 / 报错了 / 没了 | ✅ 推得到 |
| **dc-terminal-srv** | 「看和回」——画面、键盘、历史 | ❌ 推不到 |

国内可用的推送通道按现有 `Channel` trait 加实现即可，**不需要公网回调地址**的有：
企业微信群机器人、飞书自定义机器人、钉钉机器人（都是一个 webhook URL、POST 一段 JSON、免费）。
`send` 有了，`poll` 返回空表，入站交给网页——`Channel` trait 里 `poll` 允许返回空
（见 `src/channel/mod.rs`），这条路不用改 trait。

## 仓库布局

`dc-terminal` 拆成 workspace：

```
crates/dct-proto/   Request/Response、信封、PROTOCOL_VERSION（两边共用）
crates/dct/         现在的一切（客户端 + daemon）
crates/dct-srv/     中转服务
```

信封协议改一处，编译器把两边一起拦住——这是选同仓库而不是新仓库的唯一理由，也是够分量的理由。

## 不做什么

- **srv 不存任何会话内容**，连密文都不落盘。转发完就没了。断线期间的消息丢了就是丢了，
  重连之后手机重新拉一帧当前画面——终端画面本来就是"当前状态"，不是消息流。
- **不做服务端渲染、不做回放、不做内容审计**（见决定一的推论）。
- **不做手机端的 `Resize`**（见决定四）。
- **不做免扫码配对**（见决定二）。

## 分期

1. **打通链路**：workspace 拆分、信封、daemon 出网长连接、srv 路由、dc_classroom 鉴权、
   手机网页只读渲染一屏画面。
2. **配对与加密**：二维码、X25519、ChaCha20-Poly1305、设备列表与撤销。
   *(顺序是故意的：第一期先证明链路，但加密要在**开放给任何真实用户之前**落地。)*
3. **完整终端**：输入、虚拟键行、输入法、滚回历史、差量传屏。
4. **推送**：企业微信 / 飞书机器人的 `Channel` 实现。
