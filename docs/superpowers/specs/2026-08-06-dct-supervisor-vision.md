# dct 自己的智能体 —— 总体设想

**状态：** 设想已确认，未实现
**关系：** 本文是总纲，只定形状与边界。真正要实施的是
`2026-08-06-dct-llm-connection-design.md`（第一个子项目）。

## 出发点

dct 现在没有任何 LLM 能力。它是个进程主管：拉起 agent CLI、盯 PTY、判状态、
管会话。屏幕上的智能全部来自各家 agent，dct 自己一点都没有。

用户要的是：**dct 自己也有一个智能体，帮他把会话往下带。**

具体到用户实际撞到的一幕——agent 干到一半问：

> 我先把手上这条端到端验收跑完，跑完就回来改这个——还是你想现在就改？

这个问题用户每次都是同一个答法（「先跑完」）。它不值得打断人，但今天它必须打断人，
因为除了用户没人能回。

## 五件事

| # | 能力 | 性质 | 归属 |
|---|---|---|---|
| 1 | agent 要输入时通过渠道找到用户 | 人机边界 | 本轮（作为 3 的必要依赖） |
| 2 | 会话断了时说清楚出了什么事 | 人机边界 | 本轮 |
| 3 | 例行问题自己回 | **控制回路** | 本轮 |
| 4 | 摘要：改动、长会话、某一格在干嘛 | 只读 | 后续 |
| 5 | 学习用户习惯，把控多智能体多会话 | 编排 + 记忆 | 后续，独立 spec |

**1 和 3 是同一条流水线**，不是两个功能——区别只在末端往哪走。这一点直到把
「重要的问题发给用户自己决定」这条规则写下来才看清楚。

**4 和 5 各自另开 spec。** 5 尤其不能塞进本轮：它需要一个不存在的记忆层，
而且「从历史里推断用户偏好」是个比连接层大得多的设计。

## 与 2026-08-03 那次押后的关系

那次的结论是：**把 LLM 放在人机边界上，不要放进控制回路里**，并且明确把
「自动决定下一步」列为不值得做。

本轮**有意地、有限地**推翻其中一条：第 3 件事就是在控制回路里。

推翻它的理由不是改主意，而是用户给了一个具体例子，它比当初讨论的
「自动决定下一步」窄得多：

- 当初否掉的是**替用户做决定**。
- 现在要做的是**替用户回答一个他每次都同样回答的排序问题**。

守住原意的办法是那条分流规则（见下）。当初那句
「永远不替用户回答，不设超时自动选默认项」在**重要问题**上原样保留，
一个字没松。

## 分流规则

```
检测到 agent 在提问
  ├─ 重要 / 有后果  → 一律经渠道发给用户本人。
  │                   不管 dct 多有把握都不自己回，也不设超时默认值。
  └─ 例行 + 有把握  → 本地回答，记账，可撤销
     └─ 例行 + 没把握 → 同样发给用户
```

分流依据是**后果**，不是把握。两者会分叉：dct 完全可能对一件不该它拍板的事
非常有把握。

「重要」由**确定性规则先判，LLM 后判**：

1. 关键词/模式命中（钱、部署、force push、删除、动项目目录外的东西）→ 直接升级，
   **不调模型**，模型也说服不了它。
2. agent 自己把问题框成「选哪种方案」而不是「先做哪个」→ 升级。
3. 历史里没有先例 → 升级。
4. 剩下的才交给模型判，模型不确定 → 升级。

每一条岔路的默认方向都是升级给人。

## 渠道

出站到处都容易，**入站才是难点**。这决定了先做哪个：

| 渠道 | 出站 | 入站 | 结论 |
|---|---|---|---|
| Telegram | 容易 | `getUpdates` 长轮询，**不需要公网地址** | 先做 |
| macOS 通知 | 容易 | 点回 dct | 先做 |
| 飞书 / 企业微信 / 钉钉 | webhook，容易 | 需要**公网回调地址** | 可加，需基础设施 |
| 短信（Twilio / 阿里云） | 容易，花钱 | 需要专用号码 + 公网回调 | 可加；国内短信还要**模板预审**，与「转发任意 agent 提问」根本冲突 |
| WhatsApp | 仅 Business API | 仅 Business API | 可加，需企业账号 + 审核模板 |
| 微信（个人号） | — | — | **做不了。** 个人号没有 API，自动化违反条款且会封号；公众号需要企业认证加公网回调。 |

Telegram 反复胜出不是偏好问题，是因为长轮询让一台 NAT 后面的笔记本
不需要服务器、不需要公网域名、不需要隧道就能收到回复。

渠道做成可插拔的 trait，**默认是「只在终端里」**——没有渠道就不许自动回答，
这也正是第一版安全的原因。

## 硬约束（全部继承自 2026-08-03 的结论）

- **绝不进 TUI 重绘循环。** 卡住的 dct 和死掉的 agent 长得一模一样。
- **每一处 LLM 用法都要有不依赖 LLM 的退路。** 退化的方向永远是「dct 变回今天的样子」，
  不是「dct 坏了」。
- **确定性的事不要问模型。** 危险关键词判定是查表，不是推理。
- dct 保持**独立工具**：dc_llm `:8700` 是一个可配置的默认端点，不是依赖。
  这一条回答了当初悬着的那个前置问题——用户要「所有主流模型」，这个要求本身
  就把答案定成了独立工具。
