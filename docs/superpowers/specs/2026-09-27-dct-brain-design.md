## 要解决什么

dco 负责看、做、等、按流程重放，**自己不判断**。判断、定档、签票、找用户批准，全部落在 dct。
这份设计补齐 dct 这一半：dco 设计第 2 节「执行票」、第 5 节「节奏细则」、第 9 节「dct 和 dco 怎么通话」里说「dct 负责」的部分。

dco 在真机上验收时暴露了最大的风险：**只凭按钮上的字来定档，两头都会错**。
- 太松：发布流程最后一步的按钮可能写着「Next」「Continue」「OK」，会被当成「只影响自己」。
- 太严：「Don't save」被当成「保存」，没有文字的图标一律不许点。

所以真正的防线是：**流程里这一步的意图 + 执行票**，由 dct 判断、签名；按钮上的字只作第二道兜底。

## 范围和先后（用户定）

用户定的顺序：dco 第 1 步验收完，**先做本设计**，排在 dco 认图标和安卓 App 前面。本设计内部：

1. **先做**：共享库骨架、判断模块、按意图定档、执行票（「除了看以外每一步都要票」）、Mac 上的两把钥匙。
2. **后做**：动作卡片、手机批准页、排程、从纠正里学。设计写全，实施排后。

## 1. 共享库 `crates/dct-brain`

放在 dc-terminal 仓库里，跟 `dct-link`、`dct-srv` 并列。**dct 和 dco 的安卓 App 都用它，只写一份**，手机才能在电脑关着时自己判断、自己把关。

| 里面有什么 | 作用 |
|---|---|
| 判断 | 大模型、judge、游戏引擎，都是可插拔的（judge 原设计在 `src/judge`，挪进来） |
| 定档 | 按意图和动作判断档位（第 4 节） |
| 签票 | 生成执行票、签名，核对来源和流程指纹（第 2 节） |
| 排程 | 多账号错开、次数上限、最早执行时间（第 4 节） |

不放进来的：界面（dct 看板、安卓 App 界面）；钥匙的存取（Mac 用安全芯片，安卓用硬件密钥库，由调用方传进来）；网络连接（连 dco、连中转）。

两条约束：
- **没有 C 依赖**：dct 原本的规矩，同时方便安卓用 NDK 编译。
- **不直接碰网络和磁盘**：调模型、读配置都由调用方注入（跟 `llm/http.rs` 的 `with_sender` 同一个做法），测试不打网络，在手机上也能跑。

## 2. 执行票和签名

**三把钥匙**

| 钥匙 | 放在哪 | 用于 | 要不要用户动手 |
|---|---|---|---|
| 自动钥匙 | Mac 安全芯片（安卓：硬件密钥库） | `read` 之外的 `self`、`physical` | 不用；只有签过名的 dct 程序本身能用，agent 拿不到 |
| Mac 指纹钥匙 | Mac 安全芯片，`.biometryCurrentSet` | `content`、`money`，人在电脑前时 | 按 Touch ID |
| 手机指纹钥匙 | 用户手机上的 passkey（WebAuthn） | `content`、`money`，人不在电脑前时 | 刷脸或按指纹 |

**票上写什么**：
- 流程步骤的指纹 `steps_sha256`（按 dcv 统一规则 `dcv-steps-v1` 算），同时签流程正文的指纹 `body_sha256`，留作审计；单个动作则签动作本身。
- 参数、目标设备、档位。
- **最早执行时间**和有效期（第 4 节）。
- 一次性编号（dco 记住用过的，同一张票不能用第二次）。

**`content`、`money` 的票必须带用户本人的签名**（Touch ID 或手机 passkey），dco 在配对时记下这几把公钥，**自己验签**，不因为 dct 签了字就放行。即使 dct 被动了手脚，也伪造不出「用户批准过」的票。

**手机上批准**（用户选的方案：手机浏览器 + passkey）：

```
dct：把卡片内容加密 → 密文上传到 live.dataclue.cn
   → 经现有的手机通道推一条链接：https://live.dataclue.cn/approve/<编号>#<解密钥匙>
用户：点开 → 手机浏览器本地解密 → 看到人话和预演截图 → 「用指纹批准」
   → passkey 对这张票（WebAuthn challenge = 票的哈希）签名
中转：把签名转回 dct（dct 主动连中转，遵守「dct 去连别人」）
dct：核对签名 → 把票连同签名交给 dco → dco 再验一次 → 执行
```

- 中转**看不到卡片内容**：解密钥匙在 `#` 后面，浏览器不会把这一段发给服务器。
- 中转**伪造不了批准**：签名只能来自用户手机上的 passkey，而且只对这一张票有效。
- 中转最多能**不转发**：用户会看到卡片一直没被批准，但中转没法替用户批准。
- 卡片默认 **30 分钟**过期。首次使用时，在 dct 上扫码给手机注册 passkey，每台手机只做一次。
- passkey 绑定的站点固定为批准页所在的域名；WebAuthn 只能在 HTTPS 下用，所以必须走这个中转。
- 签名验证用纯 Rust 的 P-256 实现，dct 和 dco 各验一次，不引入 C。

## 3. 动作卡片

**卡片上有什么**：一句人话（「把《AI 自动玩消消乐》发到 TikTok @gaoleiai」）；具体内容（标题、正文、标签、封面、账号、时间）；**预演截图**；档位；到期时间。

**预演**：dco 先把流程执行到「最后一个对外动作之前」，比如把发布页填好，截一张图放进卡片。前面这些步骤属于 `self`，用自动票；只有最后那一步要用户签名。

| 操作 | 结果 |
|---|---|
| 批准 | 签名，执行 |
| 修改 | 直接改内容，生成新票再签；改动记下来，给第 5 节学习用 |
| 拒绝 | 可附一句原因，给第 5 节学习用 |
| 稍后 | 卡片保留，过期后重新发起 |

- **一次批准一批**：同一条视频发 5 个平台，就是 1 张卡片、5 项内容、只按 1 次指纹。签名覆盖整批票，每台 dco 只核对「自己那张票在用户签过的这一批里」。
- **出现在哪里**：dct 看板顶部「有 2 张卡片待批」；Mac 上批准时，Touch ID 弹窗里就是那句人话；手机上是第 2 节的加密批准页。两边同步，哪边批都算。

## 4. 分档和排程

**分档表**

| 档 | 例子 | dct 怎么把关 |
|---|---|---|
| `read` 只读 | 截屏、读数据 | 直接做，不要票 |
| `self` 只影响自己 | 滚动、打开页面、填表但不提交 | 自动签，事后记日志 |
| `content` 对外 | 发布、回复、改资料、**选文件上传** | 每次用户签名；dcv 里用户亲手写的规则可以放行某一类 |
| `money` 动钱 | 下单、充值 | 每次用户签名，任何规则都不能放行 |
| `physical` 物理动作 | 开关灯、断电、门锁、燃气、加热 | **自动签，事后通知**，可一键急停，能撤回的可一键恢复（用户定：「便利性第一位」，门锁、燃气也不例外） |

- 规则可以**收紧**：用户可以在 dcv 里写「门锁要按指纹」这类规则。规则只能收紧，不能放松 `money`。
- **与 dc_desktop 统一名字，各自保留规则**：dc_desktop 现在是 `read / content / money` 三档，它的 `content` 是「先预览、再自动」。统一的是这五个名字和定档方式，dc_desktop 要不要改成签名，由那边定。

**按意图定档**（dco 真机验收之后加的）
- 定档依据是**流程里每一步的意图**（「发布」「保存资料」「打开页面」），由判断模块给出。
- **用户批准流程时，同时批准每一步的档位**：dct 把「这一步是发布，属于对外」逐步标出来，用户确认一次，执行时就按这个来。流程文件本身不写档位（dcv 定的），档位随批准记录一起保存。
- 执行票签的是 `steps_sha256`：流程步骤一改，旧的批准和档位就作废。
- **按钮上的字只能把档位往高了调**，作为第二道兜底（dco 设计第 2 节）。否定词（「不保存」「Don't save」）不算保存，由判断模块识别。
- **没确认过的元素一律按最高档**：模型第一次认出来的图标、按钮都算。所以教一个新流程的那一次，每个对外点击都要用户批；为了不烦人，同一次教学里的这些点击合进同一张卡片、一次签完。

**排程**（只有 dct 看得到全局；dco 只管每一步的节奏，并且有一条 dct 调不低的速度下限）

| 规则 | 默认值（每个平台可改） |
|---|---|
| 同一平台的不同账号，两次操作之间至少隔 | 15 分钟 |
| 每个账号每天的对外动作上限 | 发帖 3 次、回复 30 条、改资料 2 次 |
| 一个会话连续做多少个动作后休息 | 30 个动作，休息 5 分钟以上 |
| 安静时段（不做对外动作） | 夜里 1 点到 7 点 |
| 同一流程连续失败 | 3 次就停下，提醒用户 |

- 默认值放在 dct 配置里；用户可以在 dcv 的 me 库里写规则**收得更紧**（例如「每个平台每天最多操作 3 个账号」），dct 排程时读取并遵守。
- **提前批准，到点执行**：明早 9 点发的视频，今晚就能批。票上写「最早 9:00、最晚 11:00」，dco 早于 9 点不做，过了 11 点作废。卡片的 30 分钟指的是「等用户批准」的时限，跟票上的执行时间窗是两回事。
- **运行统计放在 dct**：哪些流程老失败、哪个平台可能改版了，用来提醒「TikTok 发布流程可能要重新学」。不写进 dcv。

## 5. 从纠正里学

| 来源 | 记成什么 | 什么时候生效 |
|---|---|---|
| 用户在卡片上改过的内容 | 偏好草稿（例如「标题不要用感叹号」） | 用户确认后 |
| 用户拒绝时说的原因 | 规则草稿 | 用户确认后 |
| dco 在执行结果里报告学到的按钮叫法、图标名和指纹 | 流程的补充草稿 | 用户确认后，下次取流程时一起交给 dco |
| 流程走不通、模型修好的新版 | 新版流程草稿 | 用户确认后才替换正式版 |

- 都用 `dcv add` 写成来源为 agent 的草稿。**agent 写的东西永远不能给自己放行**（dcv 的防线）。
- 草稿攒着，不逐条打扰：看板上显示「有 5 条新学到的，要看看吗」，一次看完、一次确认。确认走 `dcv approve`（只给 dct 用，不进 MCP）。

## 6. dct 这一侧怎么连 dco

- **发现**：读 `~/.dco/endpoint.json`，看板上显示在线的「触手」（Mac ✅ iPhone 镜像 ✅ 安卓手机 ✅ ESP32 摄像头 ❌）。
- **配对手机上的 dco**：扫码，互换公钥；同时把用户的 Mac 指纹钥匙、手机 passkey 的公钥交给 dco，供它自己验签。
- **调用**：MCP `run_procedure` / `answer_run`（dco 已实现）。dct 对接口的要求：
  - 参数里带执行票（`self` 档是自动票），dco 验签后才执行；结果回报本次用的 `steps_sha256`。
  - 每次运行有编号，能取消，有超时。
  - 能查状态：运行中、需要帮助、被挡住、完成。dco 还没有主动推送，先由 dct 轮询。
  - `read_value` 的结果除了换算后的数，还带画面原文和位置，dct 发现异常时拿原文复核。
- **agent 不直接连 dco**：`dct mcp` 把 dco 的能力列成工具，agent 调用时 dct 在中间定档、签票，agent 手里永远没有钥匙。

## 第一个用上的功能：「看数据」

dco 会话提出、dc-vault 已核对。dct 这边负责：时间表（**只存在 dct 配置里**，dcv 不再记一份）、YouTube 和 Instagram 的接口连接器与授权（令牌放进 dct 的密钥库，配方里不写密钥）、汇总、异常提醒；屏幕流程交给 dco，**带自动签的 `self` 票**，不需要用户按指纹（教新流程的那一次除外）。

要用户另外拍板的：
- 上传到 dc_classroom 属于 `content`：每次批一张卡片，还是在 dcv 里写一条规则长期放行；网站上谁能看到这些数据。
- 走接口的前提：Instagram 要关联一个 Facebook 公共主页、建 Meta 开发者应用；YouTube 要建 Google Cloud 项目并授权。都得用户亲自操作；做不了的平台先走屏幕流程。
- 实施顺序：排在签票之后，一上线就带票，不用做两遍。

## 已知的限制

- **挡不住一个存心改 dct 本身的 agent**（同控制层设计）：同一个系统账号下的 agent 能改磁盘上的文件。用户签名这一关挡住的是伪造「用户批过」，挡不住有人改掉 dct 让它不去找用户。
- **物理动作全自动**：一旦 agent 被提示注入，可以不经用户动真实设备，包括门锁和燃气。用户知道，选择了便利。
- **中转可以拒绝服务**：它不转发，手机批准就到不了；Mac 上的 Touch ID 不受影响。
- **按意图定档依赖判断模块**：模型判断错了，还有「按钮文字只往高了调」和「没确认过的元素按最高档」两道兜底，但兜底本身也不完美。
- 平台条款禁止自动化的风险，放慢节奏只能降低，不能消除。
