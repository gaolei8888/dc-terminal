## 要解决什么

dco 负责看、做、等、按流程重放，**自己不判断**。判断、定档、签票、找用户批准，全部落在 dct。
这份设计补齐 dct 这一半：dco 设计第 2 节「执行票」、第 5 节「节奏细则」、第 9 节「dct 和 dco 怎么通话」里说「dct 负责」的部分。

dco 在真机上验收时暴露了最大的风险：**只凭按钮上的字来定档，两头都会错**。
- 太松：发布流程最后一步的按钮可能写着「Next」「Continue」「OK」，会被当成「只影响自己」。
- 太严：「Don't save」被当成「保存」，没有文字的图标一律不许点。

所以真正的防线是：**流程里这一步的意图 + 执行票**，由 dct 判断、签名；按钮上的字只作第二道兜底。

## 范围和先后（用户定）

用户定的顺序：dco 第 1 步验收完，**先做本设计**，排在 dco 认图标和安卓 App 前面。本设计内部：

1. **先做**：共享库骨架、判断模块、按意图定档、执行票（「除了看以外每一步都要票」）、Mac 上的两把钥匙。
2. **后做**：动作卡片、手机批准页、排程、从纠正里学、示范一遍系统学会（第 7 节）。设计写全，实施排后。

## 1. 共享库 `crates/dct-brain`

放在 dc-terminal 仓库里，跟 `dct-link`、`dct-srv` 并列。**dct 和 dco 的安卓 App 都用它，只写一份**，手机才能在电脑关着时自己判断、自己把关。

| 里面有什么 | 作用 |
|---|---|
| 判断 | 大模型、judge、游戏引擎，都是可插拔的（judge 原设计在 `src/judge`，挪进来） |
| 定档 | 按意图和动作判断档位（第 4 节） |
| 签票 | 生成执行票、签名，核对来源和流程指纹（第 2 节） |
| 排程 | 多账号错开、次数上限、最早执行时间（第 4 节） |

不放进来的：界面（dct 看板、安卓 App 界面）；钥匙的存取（Mac 用安全芯片，安卓用硬件密钥库，由调用方传进来）；网络连接（连 dco、连中转）。

两条约束：
- **没有 C 依赖**：dct 原本的规矩，同时方便安卓用 NDK 编译。
- **不直接碰网络和磁盘**：调模型、读配置都由调用方注入（跟 `llm/http.rs` 的 `with_sender` 同一个做法），测试不打网络，在手机上也能跑。

## 2. 执行票和签名

**三把钥匙**

| 钥匙 | 放在哪 | 用于 | 要不要用户动手 |
|---|---|---|---|
| 自动钥匙 | Mac 安全芯片（安卓：硬件密钥库） | `read` 之外的 `self`、`physical` | 不用；只有签过名的 dct 程序本身能用，agent 拿不到 |
| Mac 指纹钥匙 | Mac 安全芯片，`.biometryCurrentSet` | `content`、`money`，人在电脑前时 | 按 Touch ID |
| 手机指纹钥匙 | 用户手机上的 passkey（WebAuthn） | `content`、`money`，人不在电脑前时 | 刷脸或按指纹 |

**票上写什么**：
- 流程步骤的指纹 `steps_sha256`（按 dcv 统一规则 `dcv-steps-v1` 算），同时签流程正文的指纹 `body_sha256`，留作审计；单个动作则签动作本身。
- 参数、目标设备、档位。
- **最早执行时间**和有效期（第 4 节）。
- 一次性编号（dco 记住用过的，同一张票不能用第二次）。

**`content`、`money` 的票必须带用户本人的签名**（Touch ID 或手机 passkey），dco 在配对时记下这几把公钥，**自己验签**，不因为 dct 签了字就放行。即使 dct 被动了手脚，也伪造不出「用户批准过」的票。

**手机上批准**（用户选的方案：手机浏览器 + passkey）：

```
dct：把卡片内容加密 → 密文上传到 live.dataclue.cn
   → 经现有的手机通道推一条链接：https://live.dataclue.cn/approve/<编号>#<解密钥匙>
用户：点开 → 手机浏览器本地解密 → 看到人话和预演截图 → 「用指纹批准」
   → passkey 对这张票（WebAuthn challenge = 票的哈希）签名
中转：把签名转回 dct（dct 主动连中转，遵守「dct 去连别人」）
dct：核对签名 → 把票连同签名交给 dco → dco 再验一次 → 执行
```

- 中转**看不到卡片内容**：解密钥匙在 `#` 后面，浏览器不会把这一段发给服务器。
- 中转**伪造不了批准**：签名只能来自用户手机上的 passkey，而且只对这一张票有效。
- 中转最多能**不转发**：用户会看到卡片一直没被批准，但中转没法替用户批准。
- 卡片默认 **30 分钟**过期。首次使用时，在 dct 上扫码给手机注册 passkey，每台手机只做一次。
- passkey 绑定的站点固定为批准页所在的域名；WebAuthn 只能在 HTTPS 下用，所以必须走这个中转。
- 签名验证用纯 Rust 的 P-256 实现，dct 和 dco 各验一次，不引入 C。

## 3. 动作卡片

**卡片上有什么**：一句人话（「把《AI 自动玩消消乐》发到 TikTok @gaoleiai」）；具体内容（标题、正文、标签、封面、账号、时间）；**预演截图**；档位；到期时间。

**预演**：dco 先把流程执行到「最后一个对外动作之前」，比如把发布页填好，截一张图放进卡片。前面这些步骤属于 `self`，用自动票；只有最后那一步要用户签名。

| 操作 | 结果 |
|---|---|
| 批准 | 签名，执行 |
| 修改 | 直接改内容，生成新票再签；改动记下来，给第 5 节学习用 |
| 拒绝 | 可附一句原因，给第 5 节学习用 |
| 稍后 | 卡片保留，过期后重新发起 |

- **一次批准一批**：同一条视频发 5 个平台，就是 1 张卡片、5 项内容、只按 1 次指纹。签名覆盖整批票，每台 dco 只核对「自己那张票在用户签过的这一批里」。
- **出现在哪里**：dct 看板顶部「有 2 张卡片待批」；Mac 上批准时，Touch ID 弹窗里就是那句人话；手机上是第 2 节的加密批准页。两边同步，哪边批都算。

## 4. 分档和排程

**分档表**

| 档 | 例子 | dct 怎么把关 |
|---|---|---|
| `read` 只读 | 截屏、读数据 | 直接做，不要票 |
| `self` 只影响自己 | 滚动、打开页面、填表但不提交 | 自动签，事后记日志 |
| `content` 对外 | 发布、回复、改资料、**选文件上传** | 每次用户签名；dcv 里用户亲手写的规则可以放行某一类 |
| `money` 动钱 | 下单、充值 | 每次用户签名，任何规则都不能放行 |
| `physical` 物理动作 | 开关灯、断电、门锁、燃气、加热 | **自动签，事后通知**，可一键急停，能撤回的可一键恢复（用户定：「便利性第一位」，门锁、燃气也不例外） |

- 规则可以**收紧**：用户可以在 dcv 里写「门锁要按指纹」这类规则。规则只能收紧，不能放松 `money`。
- **与 dc_desktop 统一名字，各自保留规则**：dc_desktop 现在是 `read / content / money` 三档，它的 `content` 是「先预览、再自动」。统一的是这五个名字和定档方式，dc_desktop 要不要改成签名，由那边定。

**按意图定档**（dco 真机验收之后加的）
- 定档依据是**流程里每一步的意图**（「发布」「保存资料」「打开页面」），由判断模块给出。
- **用户批准流程时，同时批准每一步的档位**：dct 把「这一步是发布，属于对外」逐步标出来，用户确认一次，执行时就按这个来。流程文件本身不写档位（dcv 定的），档位随批准记录一起保存。
- 执行票签的是 `steps_sha256`：流程步骤一改，旧的批准和档位就作废。
- **按钮上的字只能把档位往高了调**，作为第二道兜底（dco 设计第 2 节）。否定词（「不保存」「Don't save」）不算保存，由判断模块识别。
- **没确认过的元素一律按最高档**：模型第一次认出来的图标、按钮都算。所以教一个新流程的那一次，每个对外点击都要用户批；为了不烦人，同一次教学里的这些点击合进同一张卡片、一次签完。

**排程**（只有 dct 看得到全局；dco 只管每一步的节奏，并且有一条 dct 调不低的速度下限）

| 规则 | 默认值（每个平台可改） |
|---|---|
| 同一平台的不同账号，两次操作之间至少隔 | 15 分钟 |
| 每个账号每天的对外动作上限 | 发帖 3 次、回复 30 条、改资料 2 次 |
| 一个会话连续做多少个动作后休息 | 30 个动作，休息 5 分钟以上 |
| 安静时段（不做对外动作） | 夜里 1 点到 7 点 |
| 同一流程连续失败 | 3 次就停下，提醒用户 |

- 默认值放在 dct 配置里；用户可以在 dcv 的 me 库里写规则**收得更紧**（例如「每个平台每天最多操作 3 个账号」），dct 排程时读取并遵守。
- **提前批准，到点执行**：明早 9 点发的视频，今晚就能批。票上写「最早 9:00、最晚 11:00」，dco 早于 9 点不做，过了 11 点作废。卡片的 30 分钟指的是「等用户批准」的时限，跟票上的执行时间窗是两回事。
- **运行统计放在 dct**：哪些流程老失败、哪个平台可能改版了，用来提醒「TikTok 发布流程可能要重新学」。不写进 dcv。

**暂停、急停，和给菜单栏读的状态**（用户定，2026-09-28）

小白的入口改成**菜单栏小程序 + 本机网页**（dc_desktop 目前没有上线计划）。菜单栏小程序和安装包放在新仓库 dc-local，由 dco 那边做；它只读三方公开的状态、转发按钮，自己不做判断。本机网页由谁托管（dcv 的网页、dct 的卡片、dc-local），三方以后一起定。dct 的会话列表、日志这类开发者的东西不进菜单，留在 TUI。

dct 给外部的接口是**命令行 + JSON**，不让外部直接讲守护进程的 socket 协议——那是内部协议，带版本握手，dct 一升级外部程序就会坏。命令自己去连守护进程。

- `dct status --json`：
  ```json
  {
    "schema_version": 1,
    "daemon": "up",
    "paused": false,
    "paused_by": null,
    "sessions": {"busy": 1, "idle": 2, "total": 3},
    "queue": [{"id": "…", "title": "发《…》到 TikTok", "account": "@gaoleiai",
               "earliest": "2026-09-29T09:00:00+08:00", "latest": "2026-09-29T11:00:00+08:00"}],
    "next_at": "2026-09-29T09:00:00+08:00",
    "cards_pending": 2,
    "cards_expiring_soon": 1,
    "attention": [
      {"level": "red", "kind": "dct.account_held", "text": "TikTok @gaoleiai 出现验证码，已暂停到明早 9:00",
       "until": "2026-09-29T09:00:00+08:00", "open": "schedule"}
    ]
  }
  ```
  - `attention` 是「要用户注意的事」，dct 已经判断好、按用户语言写好，菜单只管取 `level` 最高的显示和弹通知，不认识每种 `kind` 也能用。`kind` 带来源前缀（`dct.` / `dco.`），`level` 只有 `red` / `yellow`；菜单合并三方时 red 优先、同级取最新。第一批 `kind`：
    - `dct.keys_unavailable`（红）：签票钥匙没设置、Touch ID 用不了、锁屏时自动钥匙签不了——这时自动任务会全部失败；
    - `dct.account_held`（红/黄）：某账号被风控暂停，来自 dco 报回的 `risk_control`；
    - `dct.procedure_failing`（黄）：同一流程连续失败 3 次已停，「可能要重新教」；
    - `dct.quota_blocked`（黄）：防封号额度用完，导致有任务排不进去（平时的剩余额度只在安排页显示，不进菜单）。
  - 正常的状态不进 `attention`：钥匙好好的就什么都不显示。
  - `cards_expiring_soon`：10 分钟内过期的卡片数，菜单并进「等你确认」那一行。
  - 守护进程没起来时照样退出码 0，只输出 `{"schema_version": 1, "daemon": "down"}`，不吐报错（旧守护进程的情况同样处理，不能像 `ps/stop/kill/prune` 那样吐原始错误）。
  - `paused_by` 取 `null` / `"user"` / `"dco_halt"`，菜单上据此显示「你暂停的」还是「急停带停的」。
  - 字段只加不改；要改含义就升 `schema_version`。
  - 调用方每 5–10 秒查一次就够。要推送时再加 `--watch`（一行一个 JSON），第一版不做。
- `dct auto pause` / `dct auto resume`：幂等，重复按不报错；输出同 `dct status --json` 的新状态。

**暂停时 dct 做什么**
- **不再签新票**，自动签的 `self` 票、`physical` 票也不签。
- **队列挂起**，不派发。
- **已经签出去的票，dco 在急停或暂停期间一律拒绝执行**（dco 那边实现）。
- **恢复后不补做**：票上的执行时间窗照常走，过了「最晚」的票作废，重新排；不会一口气补发，那样会撞上面的次数上限。
- **不动 agent 会话**：claude / codex 这些 PTY 会话照常跑，暂停只管自动任务。
- **暂停状态写到磁盘**，守护进程重启后还是暂停——往安全的一边偏。

**和 dco 急停怎么联动**
- dco 急停**不依赖 dct**，dct 不在线也照样停。
- dco 急停时，dct 读到后**自动进入暂停**（`paused_by: "dco_halt"`）。
- **恢复两边各自解除**：dct 恢复不会顺带解除 dco 的急停，dco 恢复也不会自动解除 dct 的暂停——免得一次误操作解开两道锁。
- 菜单上的「急停」一次按到底：dc-local 先调 dco 急停，再调 `dct auto pause`。
- dco 那边（第 ① 步已合并，2026-09-28）：`halt {by?, reason?}` / `resume {}`；急停状态写在 dco 磁盘上，重启后仍是急停；急停期间动手的工具、`run_procedure`、`answer_run` 报 `error.code = "halted"`，看屏幕和 `status` 照常。dct 读 dco `status` 里的 `activity.state == "halted"`（或 attention 里的 `dco.halted`）就进入 `paused_by: "dco_halt"`。
- **菜单上只有一个「暂停 / 继续」**（用户 2026-09-28 定）：暂停 = dco `pause` + `dct auto pause`（`paused_by: "user"`）；继续 = dco `unpause` + `dct auto resume`。
  - dco 暂停时，正在做的那一步做完收尾，在下一步之前停住；`unpause` 返回暂停中的 `run_id`。**让它们接着做是 dct 的事**：dct 恢复时，对每个暂停中的流程先核对票的执行时间窗还有效，有效就调 dco `continue_run {run_id}`，过了「最晚」的就不接，让它按作废处理、重新排。
  - dco 暂停超过 30 分钟会自动取消那些流程（`run_status` 为 `cancelled`，note 写超时取消）；dct 据此不计入「连续失败 3 次」。
  - dco 暂停的格式（已合进 dco main）：`pause {by?, reason?}` → `{"paused": true, …}`；`unpause {}` → `{"paused": false, "paused_runs": [...]}`，**从不解除急停**；暂停期间动手的工具、`run_procedure`、`answer_run`、`continue_run` 报 `paused`；对正在执行的流程调 `continue_run` / `answer_run` 报 `busy`。**dco 的暂停不写盘**（重启后解除、暂停中的流程报 interrupted），dct 的暂停写盘——两边可能不一致，dct 恢复时以自己的状态为准。暂停落在 `answer_run` 里时，继续后把同一个答案再发一次。
  - `continue_run` 会阻塞到流程跑完（`done` / `needs_help` / `blocked` …）才返回，dct 要在后台调；dco 也会再核对票的时间窗，过期报 `ticket_rejected`（`expired`），和 dct 先核对是双保险。
  - 在 dct 实现这部分之前，dc-local 先自己调 `continue_run`（过渡做法，见 dc-local 设计第六节）。

这几条命令跟排程、卡片一起实现；在那之前 `dct status --json` 只能给出守护进程和会话这几项。

## 5. 从纠正里学

| 来源 | 记成什么 | 什么时候生效 |
|---|---|---|
| 用户在卡片上改过的内容 | 偏好草稿（例如「标题不要用感叹号」） | 用户确认后 |
| 用户拒绝时说的原因 | 规则草稿 | 用户确认后 |
| dco 在执行结果里报告学到的按钮叫法、图标名 | 流程的补充草稿 | 用户确认后，下次取流程时一起交给 dco |
| dco 求助时模型选中的元素（本机缓存里标「未确认」） | dco 本机缓存 | 用户确认后才启用；确认前每次照样求助（用户选的） |

| 流程走不通、模型修好的新版 | 新版流程草稿 | 用户确认后才替换正式版 |

图标的图像指纹跟坐标一样，只留在 dco 本机缓存，不进 dcv。

**草稿放在哪（用户定：路 A）**
- **偏好和规则的草稿放在 dct 自己的待确认队列里**，不进 dcv。dcv 的 `rule` 只接受 manual 或 decision 来源，agent 永远写不出规则，这是防提示注入的根本，不为草稿放开；而 dcv 里的普通知识没有草稿这道关，写进去就会被当成「你的偏好」交给 agent。用户确认后，dct 用 `dcv add --source decision` 写进 dcv，规则也这样写。
- **流程草稿照旧写进 dcv**（来源 `import:agent`，不可执行）：dco 要靠 `dcv show` 拿到完整结构，dcv 本来就有流程草稿机制。确认用 `dcv approve --sha`（只给 dct 用，不进 MCP）；带 `draft_of` 的新版确认后替换原流程，旧版留在历史里可以找回。
- dcv 2.1 配合：来源为 `import:*` 的知识在 recall 里单独标成「未经你确认的」；新增 `dcv drafts --json` 列出所有流程草稿，给看板用。
- 草稿攒着，不逐条打扰：看板上显示「有 5 条新学到的，要看看吗」，一次看完、一次确认。**agent 写的东西永远不能给自己放行。**

## 6. dct 这一侧怎么连 dco

- **发现**：读 `~/.dco/endpoint.json`，看板上显示在线的「触手」（Mac ✅ iPhone 镜像 ✅ 安卓手机 ✅ ESP32 摄像头 ❌）。
- **配对手机上的 dco**：扫码，互换公钥；同时把用户的 Mac 指纹钥匙、手机 passkey 的公钥交给 dco，供它自己验签。
- **调用**：MCP `run_procedure` / `answer_run`（dco 已实现）。dct 对接口的要求：
  - 参数里带执行票（`self` 档是自动票），dco 验签后才执行；结果回报本次用的 `steps_sha256`。
  - 每次运行有编号，能取消，有超时。（dco 已做：`cancel_run` 对正在跑的流程返回 `cancelling`，在下一步之前停；`run_procedure` 的 `timeout_s` 默认 600、范围 1–3600；等回答超过 30 分钟自动取消。`run_status {run_id}` 返回 run entry，`state` 取 `running | needs_help | blocked | done | already_done | failed | cancelled | halted`。）
  - 能查状态：运行中、需要帮助、被挡住、完成。dco 还没有主动推送，先由 dct 轮询。
  - `read_value` 的结果除了换算后的数，还带画面原文和位置，dct 发现异常时拿原文复核。
- **dco 已定要做的**（用户 2026-09-28 确认，dco 路线第 ①② 步）：
  - 状态带 `schema_version` 和 `attention` 列表，格式同第 4 节 dct 的那份；
  - 验票被拒给原因码：`expired / not_yet / bad_sig / replay / steps_mismatch / tier_mismatch / halted / busy`，dct 据此翻成人话、决定重签还是作废；
  - 用过的 nonce 写磁盘；一张签名覆盖一批票时只核对自己那张；已在跑流程时回 `busy`，不排队（排队归 dct）；
  - 结果回报 `steps_sha256`，以及实际做了几个对外动作、在哪个平台哪个账号——dct 的额度按这个算，不按签了几张票算；
  - 失败原因分类，每条带截图：`element_not_found / page_changed / login_required / risk_control / permission_missing / network / timeout / halted / ticket_rejected / unknown`。`risk_control` 让 dct 把该账号退避（第 4 节 `dct.account_held`）；
  - 换钉住的公钥必须用用户钥匙（Touch ID / 手机 passkey）签，dct 的自动钥匙签的不认；
  - 中转有鉴权之前，只接本机的 dct；
  - `~/.dco/endpoint.json` 补：设备名、平台、触手、协议版本、公钥、是否急停；
  - 预演模式（跑到最后一个对外动作前停住，截图并读回实际填写的内容，同一个 run 里等最后一张票）跟 dct 的动作卡片一起做；页面保留多久、超时怎么办，到时再定。
- **agent 不直接连 dco**：`dct mcp` 把 dco 的能力列成工具，agent 调用时 dct 在中间定档、签票，agent 手里永远没有钥匙。

## 7. 示范一遍，系统学会（用户提出，2026-09-27）

用户亲手做一遍，系统写出流程草稿，用户确认后就会了。这是第 5 节「从纠正里学」的另一个入口：纠正是「做错了改」，示范是「从头教」。

**分工**
- **dco**：录下这次示范——操作记录（每一步点了哪个元素、元素上的字、输入了什么）、关键截图、屏幕录像。录像和记录**只存在本机**，不进 dcv。
- **dct**：把示范交给判断模块里的视觉模型，写成按意图的流程草稿；草稿用 `dcv add` 写进 dcv（来源先标 `import:agent`，dcv 2.1 起标 `import:demo`），流程里只记一个示范编号（dcv 2.1 提供这个字段）；然后放到看板上，**跟录像左右并排**给用户确认。
- **dcv**：校验草稿、存草稿、确认后存正式版。

**模型写草稿的要求**
- 不写坐标；步骤只用 dcv 的封闭动作词表；按意图写（「点保存」，不是「点右上角」）。
- 示范时填的具体值抽成参数，参数只写名字。**哪些值算参数由模型提议、用户在确认时改**：示范里输入的「Lei Gao AI」是这次的名字，应该是参数；「简介」这个栏目名是流程的一部分，不是参数。
- 带上完成标志和注意事项（比如「TikTok 简介带中文会被悄悄丢掉」这类示范里踩到的坑）。
- **草稿被 dcv 拒绝时，把 dcv 的错误原因原样交回模型再改**，最多 3 轮；3 轮都不过，就把录像和最后一版草稿一起放上看板，请用户手动改或重录。**绝不绕过 dcv 的校验。**

**确认**
- 看板上左边录像、右边草稿；每一步跟录像里的时间点对齐，点一步就跳到录像对应的位置。
- 确认走现有的 `dct procedure approve`：用户同时确认每一步的档位（第 4 节），按 Touch ID，dct 再调 `dcv approve`。示范出来的流程**不因为是用户亲手做的就自动可信**：写草稿的是模型，模型可能理解错。

**标注和质检也用同一个办法**
用户亲手标几条、质检几条作为示范，模型据此写出**标注规范和判例**的草稿，按路 A 放进 dct 的待确认队列（规范和判例属于规则、偏好，不是流程），用户确认后 dct 以 `decision` 来源写进 dcv。

**要注意的**
- **隐私**：录像里是用户的真实屏幕。录制时 dco 不录密码框的内容（系统标成安全输入的一律打码）；发给模型的只有关键截图和操作记录，不发整段录像；录像在流程确认后保留 7 天就删，用户可以改。用户知道截图会发到哪个模型。
- **示范本身不需要执行票**：示范是用户自己在操作，dco 只是在旁边看（`read` 档）。
- **依赖**：视觉模型要走判断模块；在拿到 DC 网关密钥之前，可以先借本机已装好的 Claude Code 这类 agent 来写草稿（Laya 的做法）。

**顺序**：排在执行票、动作卡片之后。它依赖看板的草稿确认界面，也依赖 dco 的录制功能（dco 那边另做）。

## 9. 游戏的快速判断（dc-octo 会话转述，用户 2026-09-30 定：归 dct）

研究全文在 dc-octo 仓库 `docs/2026-09-30-small-models-for-game-play-research.md`（现已在 main）。
起因：Candy Crush 由会话里的大模型看图选步，每步 30～40 秒、每步花 token。dco 不做判断，所以「下一步怎么走」归 dct。

- **2026-10-02 按 dc-octo 实验结果改写**（dc-octo main `docs/experiments/2026-09-30-fast-decision-*.md`，交接文档 `…-handoff.md`）。
  原先写的「首选 Laya、Jeff 备选、给每个交换打分」作废：
  - 测试 A（100 题 × 中英文，M4 32GB）：三消上规则 100%、Jeff-0.8B 27%（中文 67%）、Laya 英文 43% / 多语言 57%、随便选 39%；
    没有一个模型达到 p95 ≤ 50 ms。**Laya 近期不再投入**（用户 2026-09-30 同意），**nomic 不进产品**（用户 2026-10-01 定）。
  - 规则的 100% 读的是结构化的「后果」（facts），不是文字——三消这类能用代码算出后果的游戏，直接规则打分。
  - 危险动作**靠规则拦，不靠模型把握**：几个模型都会很有把握地选「花金条买步数」「付款」，规则一次都没选。
- **三消的做法**：dco `read_grid` 读棋盘 → dct 用代码列出全部合法交换并算出后果（消几颗、出不出特殊糖、位置）→
  规则先拦危险动作 → 规则打分取最高 → 拿不准或认不出（特殊糖、障碍）的交给大模型或看图模型。
  小模型只留给规则说不清的游戏，等有训练数据再比（Jeff 微调在另一台电脑上做，显卡待定）。
- **看图认盘**：测试 B 的 Qwen3-VL-4B 一次 1～3.5 秒；真机普通棋盘零样本 45/45，特殊糖一出现就读错。现在普通格交给 `read_grid`，
  它认不出的才交给看图模型。
- **攒样本照旧**：大模型玩的每一步记一条（棋盘、全部合法交换、大模型的选择、结果）。大模型的选择只是弱标签，没被选中的动作不算错；
  训练、校准、测试按游戏 / 关卡 / 会话分组切开。
- **模型不打包进 dct**：按任务在 dcv 登记，用到才下载；正式版用 ONNX Runtime 跑，不给用户装 Python。
- **验收**：一步 1 秒以内（dco 读棋盘 + dct 选 + dco 划）；和大模型一致的比例，做实验时定目标。
- **dct-brain 自己的危险词表要重做**：dc-octo 的盲测（`docs/experiments/2026-09-30-danger-rules.md`，410 条）里，
  dco `tier_for_label` 和 dct-brain `tier::raise` 只认出约三成危险按钮，删除、授权、安装三类几乎全漏；按五类原则重写的实验规则
  （`experiments/fast-decision/bench/danger_rules.py`）认出 78%（只看字）/ 83%（加页面），误拦 18～19%。
- **dco 的 `read_grid` 已做好**（dc-octo main bc15e10，设计 `docs/superpowers/specs/2026-10-02-read-grid-design.md`）：
  只读档、不要票，急停/暂停时也能用，锁屏回 `screen_locked`。参数 window、region{x,y,w,h}（窗口内 0～1）、rows/cols（1～32）、
  inset（0.2～1，默认 0.6）。返回 cells[r][c] 类别号（**只在本次有效，跨次按 classes 的 rgb 找最近的类**）、classes[{id,rgb,count}]、
  odd[r][c]（条纹糖等；包装糖目前标不出）、frame_age_ms（可能没有）、elapsed_ms。错误 bad_request / not_a_grid（>16 类）。
  实测 p50 1.45 ms，首次约 170 ms。只差深浅或黑白灰为主的棋盘（围棋、2048）可能被并成一类且不报错。
  调参参数已做好（dc-octo main 94e1544），都可选、不给时结果不变、越界回 bad_request：class_de（默认 24，10～40）、
  top_div（整数，默认 5，2～10）、odd_share（默认 0.2，0.05～0.5）、detail（布尔，true 时多返回 detail{dominant 每格主色 [r,g,b], share 每格本色占比}）。
  例：1712 关 odd_share 调到 0.15，包装糖也标成 odd、不误标普通糖。
  read_grid 和 see 都多返回 observation_id（obs-16 位十六进制，重启不重复）和 observed_at_ms（拍下这一帧的 Unix 毫秒）；
  **dct 的每个决定都记下所依据的 observation_id**，dco 暂不拿它拦截。
- **新游戏由 AI 自动校准**（用户 2026-10-02 定，归 dct）：大模型认出棋盘范围、行列数、每类叫什么 → dco 读一帧、大模型逐格抄同一帧、
  比两边分组 → 对不上就在允许范围内调参数再比 → 结果给用户确认、存进 dcv → 调不出来就判定不适合读棋盘，改用看图模型。
  校准截图留在本机、由 dct 保存；dcv 只存资料、确认记录和截图指纹（sha256）（用户定）。
  重新校准的时机：游戏改版；读出的类别数和 dcv 记的不一样；大模型抽查对不上（抽查由 dct 安排，比如每局开始一次，不进每一步）。
- **没解决的口子**：纯数字的关卡按钮、无字的棋盘格，dco 按「对外」拦；当天是用原地轻点的 swipe 点过去的，等于绕过了按字定档。
  正式放行规则由 dco / dcv 定，dct 签票可能要参与；在那之前这条绕路不算放行。

## 已知的限制

- **挡不住一个存心改 dct 本身的 agent**（同控制层设计）：同一个系统账号下的 agent 能改磁盘上的文件。用户签名这一关挡住的是伪造「用户批过」，挡不住有人改掉 dct 让它不去找用户。
- **物理动作全自动**：一旦 agent 被提示注入，可以不经用户动真实设备，包括门锁和燃气。用户知道，选择了便利。
- **中转可以拒绝服务**：它不转发，手机批准就到不了；Mac 上的 Touch ID 不受影响。
- **按意图定档依赖判断模块**：模型判断错了，还有「按钮文字只往高了调」和「没确认过的元素按最高档」两道兜底，但兜底本身也不完美。
- 平台条款禁止自动化的风险，放慢节奏只能降低，不能消除。
