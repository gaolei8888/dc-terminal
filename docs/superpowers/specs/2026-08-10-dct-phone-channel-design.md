# dct 手机连接 —— 设计

**状态：** 设计已确认，未实现
**总纲：** `2026-08-06-dct-supervisor-vision.md`（五件事里的第 1 件）
**前置：** `2026-08-06-dct-llm-connection-design.md`（连接层已实现并合入 main）

## 目的

用户说得很直接：**让 agent 不要停下来。**

这句话是本设计的判准，不是背景。每一个决定都拿它检验一遍。

但要诚实：**手机通道让 agent 停得短，不能让它不停。** 它把干等从「到你回到
电脑前」（几小时）缩短到「到你看一眼手机」（几分钟）。你睡着的那八小时，
agent 照样停着——消息发出去了，没人回。

**本轮的成功标准就写成这一句：把干等从「到你回到电脑前」缩短到
「到你看一眼手机」。** 让它彻底不停留给下一轮的自答（总纲第 3 件事）。

## 范围

**要做：**

- 出站：agent 停下来 / 报错 / 自己没了 → 推消息到手机
- 入站：手机上回一句话 → 敲进对应的 agent
- 主动发：不是在等你的时候也能往一个会话里发指令
- 四项智能处理（编号选项、听懂自然语言回复、路由更准、多条合并）

**不做，且都是用户明确否掉的：**

- **不做自答**（总纲第 3 件事）。留给下一轮。
- **不做超时自动继续。** 总纲那条「不设超时自动选默认项」原样保留。
  没人回就停着——这是用户在明知它与「让 agent 不要停下来」冲突的情况下
  做的选择。

  > **但有一个例外已经确认，留给下一轮做，不在本轮范围内。** 见下面
  > 「回合结束 vs 等你拍板」。
- **不做深夜分级。** 手机自己的勿扰模式管这件事，dct 不掂量你的消息，
  也就不会把一件你真该马上知道的事拖到早上。
- **不做 macOS 通知。** 总纲把它和 Telegram 一起列进「先做」，本轮砍掉：
  这个功能的全部价值是**你不在电脑前**，而 macOS 通知只有你在电脑前才看得见。
  它与本轮目的正交。
- **不做 ask_human 工具。** 那要给每个 agent 单独装工具端，是另一个子项目。
  本轮全靠已有的屏幕检测。

## 渠道：只做 Telegram

已与用户确认：**本机能稳定访问 Telegram**，按总纲走。

短信这条路被排除，理由不是麻烦而是做不了：出站要买服务商按条计费，入站要
专用号码**外加公网回调地址**，而国内短信还有**模板预审**——发出去的内容必须
事先报备审核，与「把 agent 临时冒出来的问题原样转给你」根本冲突。

Telegram 之所以是第一个，全部原因是 `getUpdates` 长轮询让 NAT 后面的笔记本
不需要服务器、不需要公网域名、不需要隧道。渠道做成可插拔 trait，但**本轮
只有一个实现**。

## 架构：渠道住在守护进程里

三个候选，选 A。

**A（选中）——渠道住在 daemon 里。** daemon 已有 200ms 的 tick 在算状态迁移
（`session.rs::tick`），会话自动命名就挂在「第一次 `Working → Idle/Asking`」
这个钩子上。手机推送是**同一个判据的第二个消费者**，不用新造检测。再起一个
后台线程做长轮询。状态一变就知道，不动协议，**daemon 活着它就活着**——这正是
产品本身的定位。

**B——独立进程 `dct bridge`。** 否掉。`src/proto.rs` 里**没有任何推送或订阅
机制**（已核实），客户端全是一问一答。bridge 只能靠不停 `List` 轮询才能发现
「某个会话停下来了」，要么为它强推一套订阅进协议（本轮不值这个价），要么接受
轮询延迟。更麻烦的是生命周期：谁启动、谁重启、用户要不要管它——**多一个需要
照顾的进程，与「关掉界面就不用再想它」直接打架。**

**C——渠道住在界面里。** 直接否掉。界面会退出，而这个功能的全部意义是人不在。

## 组件与边界

三个新文件，其余不动。

```
src/channel/mod.rs       渠道 trait + 事件类型
src/channel/telegram.rs  唯一的适配器：getUpdates 长轮询 + sendMessage
src/bridge.rs            连接层，唯一有状态的地方
```

**渠道 trait** 两个方法：发一条（返回渠道那边的消息 id），取新消息（阻塞最多
若干秒）。收到的消息带「它回复的是哪条」。**传输层注入**，沿用 `verify.rs` 与
`llm/http.rs` 已有的套路——零网络可测。

**`bridge` 只记两样状态：** 消息 id → 会话 id 的映射（长按回复靠它定位），
和「当前会话」（不带回复的消息发给谁）。除此之外不存任何东西。

**依赖方向单向：** `bridge` 用 `channel`，`bridge` 调 `session` 已有的写入路径。
**`session.rs` 不认识 `bridge`**——tick 只往队列里投事件，投完就走。

**硬约束：tick 线程绝不碰网络。** 200ms 的循环里一次 HTTP 调用就能让整个守护
进程卡住，而卡住的 dct 和死掉的 agent 在屏幕上长得一模一样。出站消息全部由
bridge 自己的线程发。

**bot token 走已有的 `SecretStore`**（`~/.dct/secrets.toml`，0600），
**不新建第二个密钥存储。**

## 出站：什么时候发，发什么

### 三个事件

| 事件 | 判据 | 现状 |
|---|---|---|
| 干完一轮停下来了 | `was == Working && next ∈ {Idle, Asking}` | 已存在，auto-name 在用 |
| 报错了 | `next == Failed && was != Failed` | 已存在，`request_explanation` 在用 |
| 会话自己没了 | `tick` 收尸那条路，`journal::Death::Vanished` | 已存在 |

第三个也推：你在外面，一个 agent 悄悄死了，这是你最该知道的事。

### 三道门

推之前全部满足才发：

1. `s.is_agent` —— 普通命令行会话不推
2. `!s.first_input.is_empty()` —— **启动画面防线**
3. 渠道已配置

第 2 条不是锦上添花。`session.rs` 里 auto-name 那段注释解释了原因：真实
profile（claude/codex/glm/kimi/deepseek/qwen-api）**全都只声明 `busy_pattern`**，
`classify()` 在 busy 串不在屏幕上时就判 `Idle`，而刚创建、还停在启动画面上的
会话正是这样。没有这道防线，**每开一个会话手机就响一次。**

### 内容分两档，这是隐私边界

**没配 `[llm]`：** 只发元数据——会话名、agent、项目、出了什么事。

```
修登录白屏 · claude 在等你回话
```

**屏幕上的内容一个字都不出这台机器。** 会话名是自动命名功能早就生成好的，现成的。

**配了 `[llm]`：** 模型读一眼屏幕，多产出一句话。

```
修登录白屏 · claude 在等你回话
它问：先把端到端验收跑完再改，还是现在就改？
  1 先跑完
  2 现在改
```

**去 Telegram 的只有模型产出的那几句，原始屏幕内容不去。** 屏幕内容只走到模型
那里——那正是 `config.rs` 里 `[llm]` 必须由用户显式打开的原因，现在它管住了
**两个去处**而不是一个。

由此：**不配 `[llm]` 不是残废模式，是更严的模式。** 功能照用，消息简略些。

### 消息格式

守总纲那条：一句话、自足、**没有路径、没有 diff、没有代码块**，选项同时编号
和带标签。约束来自「这条消息要经得起被念出来」（口述回复是「就第二个吧」而
不是 `2`），但它同时也是隐私护栏。

### 防抖

同一个会话**回到 `Working` 又停下来**，才算下一个事件；短时间窗内的抖动合并
成一条。用户选的是「宁可多吵也不漏」，但状态在两个值之间来回跳不是「多」，
是噪音。

## 入站：收到之后敲给谁

### 这一轮完全不碰 `Asking`

`tick()` 里有一句 `if s.state == Asking { continue; }`——一旦进入 `Asking`，
状态机冻结，不再扫屏幕。那是留给将来 `ask_human` 的：agent 真的阻塞在一个
工具调用上，屏幕不会再变，扫也没意义。

本轮不是那个场景——agent 没阻塞，它停在输入框前面，屏幕还会动。**拿 `Asking`
表示「已经推到手机了」会造出一个真 bug：** 用户选了「没人回就停着」，那这个
会话可能永远冻在 `Asking`；等他回到电脑前直接在 dct 里敲字回答了它，dct 也
不会发现——屏幕早就不扫了，状态永远停在那儿。

**「已经推到手机了」是一个独立的标记，不是状态。** 状态机保持今天的单一职责。

> 给后来的人：看到 `Asking` 就想拿来用是很自然的，上面这段就是为你写的。

### 路由规则，严格按这个顺序

1. **带回复的** —— 查消息 id → 会话 id 映射，直接定位。**永远不反问。**
2. **用户显式 `/use` 过，且那之后还没回复过任何推送** —— 发给 `/use` 指定的
   会话。**这一条必须排在「唯一在等」前面**：用户切过去就是想跟那个会话说话，
   此刻另一个会话恰好在等，不能把他的话抢走。
3. **只有一个会话推过消息还没得到回应** —— 就是它。
4. **有好几个在等** —— 模型先猜（见智能层），**不确定就反问**，回一条列出来
   让用户点。
5. **一个在等的都没有，也没 `/use` 过** —— 告诉用户先 `/ls`。**什么都不敲。**

第 2 条的「那之后还没回复过任何推送」是它的失效条件：用户一旦长按回复了某条
推送，说明他的注意力已经转到那个会话上，`/use` 的指定作废，回到第 3 条。
不这样的话，一次 `/use` 会永久劫持所有不带回复的消息。

### 主动发指令

就是第 2 条和第 5 条那两种情况。当前会话用两个命令管：

- `/ls` —— 列出所有会话
- `/use 3` —— 切过去

**只有这两个命令，不做别的。**

「当前会话」和消息 id 映射一样存在内存里，**守护进程重启就没了**——重启后
等同于从没 `/use` 过，走第 5 条。

### 安全：只认一个 chat id

**这是整个功能最危险的地方。** Telegram bot 的用户名是公开可搜的，**任何人都能
给这个 bot 发消息**——而这个功能会把消息敲进用户的终端。

**只接受配对过的那一个 chat id，其余一律丢弃。**

配对是一次性的：填完 token，dct 开始轮询，**第一个给 bot 发消息的人**被记为
主人，之后不再接受第二个。

界面见下一节。

## 界面

### 设置页要先改结构

`View::Settings` 今天是一个纯语言列表——`ListState` 的下标**直接映射
`Lang::all()`**（`settings_view.rs::handle_key` 的 `Enter` 分支）。加进第二项
就得先把它从「选语言」改成「选设置项，进去再操作」：

```
设置

  界面语言        中文
  手机通知        已连上 · @lei
```

这是本轮唯一一处对既有界面的结构改动，**必须单独一个任务做完并通过测试**，
不要和手机通知的逻辑混在一起。

### 手机通知页

从设置页进。它要显示的东西 `EnterSecret` 一个都表达不了，所以是独立的一页：

```
手机通知

  状态    等你给 @your_bot 发一条消息
          在 Telegram 里搜这个名字，随便发句话就配上了

  令牌    已填，已验证
  主人    还没有

  Enter 重新填令牌    r 重新配对    x 关掉手机通知
```

**状态那一行是这一页存在的全部理由。** 四种取值，每一种都带下一步：

| 状态 | 显示 |
|---|---|
| 没填令牌 | `还没开。按 Enter 填一个机器人令牌` |
| 填了、没配对 | `等你给 @your_bot 发一条消息` + 一句怎么做 |
| 配上了 | `已连上 · 主人 @lei` |
| 连不上 | 人话 + 下一步，例如 `令牌被撤销了，按 Enter 重填` |

### 令牌填入复用已有的验证机制

`View::EnterSecret` 已经带 `SecretPhase::Verifying` 和「密钥不对」的反馈，
这套原样复用：Telegram 的 `getMe` 就是验证端点，和现有 `Request::VerifySecret`
打真实端点验密钥是同一件事，**不新造一套验证流程**。

填错一半的令牌当场就知道，而不是十秒后在一个没反应的页面上猜。

### 配对是异步的，界面靠轮询

守护进程填完令牌就开始长轮询等第一条消息，而协议是一问一答、界面本来就在轮询
（`client.rs`）。所以手机通知页在打开期间**每次刷新问一次状态**即可，
**不需要为它引入推送**——这与「B 方案被否掉」的理由一致：本轮不动协议的形状。

### 令牌存哪

存进已有的 `SecretStore`（`~/.dct/secrets.toml`，0600），用一个 profile 不可能
占用的保留名字。

**它不会出现在密钥页（`c`）里**，因为那一页是**遍历 profiles** 再查
`has_secret`（`pick.rs`），不是遍历 `secrets.toml` 的键。

> 这一条是隐式成立的。将来谁把密钥页改成遍历 `secrets.toml`，这个保留名字
> 就会作为一个不存在的 agent 冒出来。改那里的人请回来看这一句。

### 回执必须有

敲进去之后回一条短的「已发给 修登录白屏 · claude」。用户在外面看不见终端，
没有回执他不知道这句话到底进去没有。

### 全程记 journal

推了什么、收到什么、敲进了哪个会话。journal 的存在理由本来就是「我不在的
时候那个 agent 是怎么没的」，这件事正好是它。

## 智能层

用户要求「尽量多做智能处理」。先分类，因为两种智能的性质完全不同：

- **不替用户做决定的智能** —— 让消息更好懂、路由更准、把黑话翻译成人话。
  最坏情况是没帮上忙。**本轮全做。**
- **替用户做决定的智能** —— 就是自答。最坏情况是替他答错了。**本轮一个都不做。**

### 四项，按时间要求分类

**合并不需要模型。** 一个时间窗内的多个事件凑成一条消息，纯规则。
`[llm]` 配没配都可用。

**出站的智能可以慢**（编号选项、摘要）——消息晚几秒无所谓。走
`request_explanation` / `request_name` 已经建好的范式：**先把不依赖模型的兜底
同步写进去**，再起线程去问，硬超时，迟到的答案直接丢。兜底永远先就位，所以
模型再慢消息也发得出去，只是简略。

**入站的智能必须快，而且是阻塞的**（听懂回复、猜路由）——用户在手机上等回执，
不能异步。它跑在 bridge 自己的线程里，卡住不影响任何会话，但**必须有硬超时**，
否则 bridge 线程死了等于整个手机通道死了。

### 红线：只转格式，不造内容

「听懂自然语言回复」这一项的红线，已与用户确认保留：

- agent 要的是**自由文本**时，模型**完全不介入**，用户说什么原样敲什么
- 只有 agent **明确摆出选项**时才做映射（「就第二个吧」→ `2`）
- 映射不确定 → 原样发

理由：模型一旦开始润色用户的话，敲进 agent 的就不再是他说的话了，而这件事
他在手机上看不见，只能看见一条「已发送」的回执。

代价（用户已接受）：手机上语音输入一段车轱辘话，dct 一字不改地敲进去，
不替他整理。

### 猜路由的红线

**模型只在路由规则第 4 条（有好几个在等）介入**，其余四条都是硬规则，模型
碰不到。前三条已经确定了答案，没有什么可猜的；第 5 条没有候选，猜也无从猜起。

在第 4 条里，模型给建议，但**不确定就还是反问**。**永远不因为「模型有把握」
跳过那一问**——敲错 agent 的代价比多问一句大得多。

这一条与总纲「分流依据是后果，不是把握」是同一个道理。

### 每一项坏了往哪退

| 智能 | 坏了之后 |
|---|---|
| 编号选项 | 消息里没有选项，只剩「修登录白屏 · claude 在等你回话」 |
| 听懂回复 | **用户打的字原样敲进去**——正是红线的自然结果 |
| 猜路由 | 退回三条硬规则 |
| 合并 | 不会坏 |

**退化方向永远是「dct 变回今天的样子」，不是「dct 坏了」。** 用户会看到消息
变笨，不会看到功能消失，更不会看到东西敲错地方。

## 错误处理

| 出什么事 | dct 怎么办 |
|---|---|
| 网络断了 | 退避重试，会话完全不受影响。界面一行很轻的提示，不弹窗不打断 |
| token 无效 / 被撤销 | **401 不重试**，重试一万次还是 401。界面说人话：「手机通知连不上了，按 `c` 重新填」 |
| 断网期间攒下的消息 | 排队，**有上限，且合并**。断网八小时不该在恢复瞬间收到五百条，该收到一条「6 个会话停了」 |
| bridge 线程 panic | **绝不拖垮守护进程。** 手机通道死掉是遗憾，会话跟着死是灾难 |
| 守护进程重启，手机上还躺着旧消息 | 见下 |

### 守护进程重启这一条要单独说

消息 id → 会话 id 的映射在内存里，重启就没了。用户长按一条昨天的消息回复，
dct 已经不认识它。

**这时绝不能退化成「发给当前会话」**——那正好是敲错地方的路径。正确行为是
回一句「这条消息对应的会话已经不在了」，**什么都不敲。**

## 测试

渠道在 trait 后面、传输层注入，**全部零网络**：401、超时、畸形回包、陌生
chat id 都能测。沿用 `verify.rs` 与 `llm/http.rs` 的套路，不新发明。

### 真正的回归套

这三条是唯一能实际伤到用户的地方：

1. **陌生人给 bot 发消息一律丢弃** —— bot 用户名公开，这条一破，任何人都能
   往用户终端里敲字
2. **新建会话不推消息** —— 那道 `!first_input.is_empty()` 防线，一破每开一个
   会话手机就响
3. **守护进程重启后，旧消息 id 不会被敲进任何会话**

### 其余

- **路由五条规则的表驱动测试**，其中必须单独覆盖第 2 条压过第 3 条
  （`/use` 过之后，另一个会话正在等，话仍然发给 `/use` 指定的那个），
  以及它的失效（长按回复过一次之后，`/use` 的指定作废）
- 模型超时后「用户打的字原样敲进去」
- **防抖**：一个会话在窗口内 `Idle → Working → Idle` 反复抖动只产生一条消息；
  窗口之外的第二次 `Working → Idle` 是一个新事件，照发
- 三道门各自单独可测（非 agent 不推、`first_input` 为空不推、没配渠道不推）
- **设置页改结构之后语言仍然切得动**——那是既有功能，回归它比新功能出问题更糟
- 手机通知页四种状态各自渲染出正确的下一步文案（纯函数，不碰网络）

## 回合结束 vs 等你拍板（下一轮，已确认方向）

**不在本轮范围内**，记在这里是因为它是上面「没人回就停着」那条的唯一例外，
而且方向已经和用户确认过了。

用户给的实例：agent 输出完一段结论，最后写「现在动手，从 `@dc/model-providers`
开始」，然后停了。

**它没有在问任何问题。** 它已经决定好下一步，只是把回合交还给了用户。
让它继续只需要一个空回车，**不替用户做任何决定**。

这与总纲里那个例子（「先跑完验收还是现在改？」）性质不同：那个是真的在问、
真的要用户选一个，自动接上就是替他做决定。这个只是回合结束。

**危险在于把两者认错。** 很多 agent 把空回车当成默认选项的确认——一旦
dct 把「先跑完还是现在改」误读成「只是回合结束」并送进一个空回车，
它就替用户选了，而用户以为它只是继续。

**已确认的判定方式：两道闸，先查表后问模型。**

1. **关键词/模式先查表** —— 最后那几行里出现问号、选项列表、审批提示，
   一律当作在等用户，**推到手机，不自动接**。
   **这一步不调模型，模型也改不了它的判定**（同总纲「危险关键词判定是查表，
   不是推理」）。
2. 查表没排除的，**才**交给 `[llm]` 判断「这是在等人拍板，还是只是回合结束」。
   **模型不确定就不动。**

没配 `[llm]` 时第二道闸不存在，于是只有第一道闸放行的才自动接——那是最保守的
方向，符合「退化成 dct 变回今天的样子」。

## 未验证 / 风险

按 dct 的惯例，没跑过的一律记成未验证，不当作跑过。

| 项 | 状态 |
|---|---|
| Telegram `getUpdates` / `sendMessage` 真实端点 | **未验证。** 需要真 bot token 跑一次。这与既有的四个 vendor base_url 是同一类风险 |
| 「停下来就发」在真实使用下的消息量 | **未验证。** 实现取 30 秒防抖窗口作为起点，但这个数字是拍出来的，必须实测调整。它偏小会吵人，偏大会漏掉真正的第二个事件 |
| 模型抽编号选项的产出质量 | **未验证。** 与 `explain_prompt` 同一类问题：管道通不通好验，产出好不好只能实测 |
