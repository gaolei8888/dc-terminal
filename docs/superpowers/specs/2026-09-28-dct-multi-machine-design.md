# dct 多电脑：几台电脑上的智能体互相留言、派活 —— 设计

**状态：** 用户已审（2026-09-28），进入实施计划。第 1–3 段内容 2026-09-28 在对话里逐段确认过；「和之前讨论不一样的地方」一节是写文档时查代码后做的修正，需要用户再看一眼。

## 现状（2026-09-28 查代码）

- **中转 dct-srv**：信封路由（`/link/poll`、`/link/send`、`/link/ask`）已经写好，有测试。但是：
  - 没有鉴权：`crates/dct-srv/src/lib.rs` 的 `check()` 里写着 `TODO(任务 5)`，token 没人验；
  - 程序只肯监听本机地址（`main.rs` 的 `must_be_loopback`）；
  - 所以它**从没上过公网**。dataclue.cn 上在跑的只有公开直播列表。
- **dct 守护进程**：`src/link.rs` 会主动连中转、长轮询收信封，只在本机开发时用过。
- **信封是明文**：原设计第二期的 X25519 加密还没做。
- **没有任何「电脑 ↔ 电脑」的路**：`EndpointKind` 只分 `Computer` 和 `Phone`，中转只做「手机找电脑」。智能体也没有给别人留言的工具。
- **手机推送**走 Telegram（`src/channel/telegram.rs`），跟中转无关。

结论：地基有一半（路由、长轮询、信封格式），缺的是鉴权、加密、上线，以及「电脑当收件人」。

## 第 0 段：沿用 dct-srv 原设计的四条决定

这四条是 2026-08-23 用户当场拍的板，本设计不改：

1. **中转不解析内容**，只按信封上的收件人转发。
2. **端到端加密**：中转只知道谁连了谁、多少字节。信封用 X25519 协商密钥、ChaCha20-Poly1305 加密。中转算不出密钥。
3. **身份用 DataClue 账号**，一个账号多台设备，设备可以撤销。
4. **中转不存任何会话内容，连密文都不落盘。**

第 4 条直接影响离线留言的做法，见第 2 段「对方不在线」。

## 第 1 段：电脑的身份，以及怎么连成一组

### 每台电脑的两样东西

- **账号凭据**：证明「这台电脑属于哪个 DataClue 账号」，中转凭它决定让不让你连。存在 `~/.dct/secrets.toml`（已经是 0600 / Windows 单条 ACL）。
- **电脑钥匙**：一对 X25519（加密）加 P-256（签名）。公钥就是这台电脑的身份证。
  - Mac 的签名钥匙放安全芯片，复用 `src/keys`；
  - Windows / Linux 放本机文件（0600 / ACL）。
  - 加密钥匙在所有平台都放文件：安全芯片不做 X25519。

### 组 = 群

- 现在只有一个组「我的电脑」。数据结构从一开始就按「群」设计：群 id、群主、成员名单。
- **成员名单由群主签名**，每台电脑都存一份。中转只按名单转发，但名单是谁签的它说了不算，所以中转没法偷偷往组里加电脑。
- 名单每项：电脑名（用户起的，组内不重复）、签名公钥、加密公钥、加入时间。

### 加一台新电脑
> **已被替换（2026-09-30）：** 这一节已经被 `2026-09-30-dct-invite-code-design.md`（6 位邀请码 + SPAKE2，dct-invite-v1）替换，代码里已经没有这套流程；下面的原文只留作记录。


1. 新电脑上运行 `dct login`：浏览器里用 DataClue 账号确认（复用 device code 流程）。登录后它能连上中转，但还不在组里。
2. 组里任意一台已有的电脑上弹出：「一台叫 公司Windows 的电脑想加入，两边屏幕上的 6 位数字一样吗？」
   - TUI 里是顶部一行，按 y 同意；dc_desktop 里是一张确认卡片。
   - 6 位数字由两台电脑的名字、公钥，加上两边各出的一次性随机数算出，两边各自显示。算法见下面「6 位数怎么算」。
3. 用户核对数字一致，点同意。已有的电脑用群主钥匙重签名单，发给所有成员。
4. **第一台电脑**登录后直接成为群主，名单里只有自己。

**为什么要核对数字**：原设计第二条要求配对「必须走一条不经过服务器的信道」，原设计用的是当面扫二维码。自己的两台电脑常常不在一个房间，扫不了码。所以改成让人眼核对两块屏幕上的数字：服务器就算伪造公钥，每冒充一次也只有一百万分之一的机会凑出一样的数字，而且两块屏幕上能亮几个数字都有上限：老电脑在一个加入窗口（10 分钟）里最多亮 20 个；新电脑一次 `dct join` 最多问 16 台（中转报的在线列表去重之后，超过 16 台就一台都不问、一个数字都不给看，请用户过会儿再试），它没法一直试下去。代价是核对这一下必须人来做，不能自动。

**为什么数字里要有随机数、还要先承诺**（2026-09-28 终审 C1 之后改）：6 位数只有一百万种。如果数字只由两台电脑的公钥算，中转看得见所有公钥，它可以一把一把地生成假钥匙，直到某一把算出来的数字恰好等于新电脑屏幕上的那个——一台笔记本几秒钟的事，对着长期不变的钥匙还能提前算好一张表。所以两边各出一个一次性随机数混进去，而且谁都不能看了对方的再挑自己的：新电脑先只交一个「承诺」（随机数的指纹），已有的电脑收到承诺之后才出自己的随机数，新电脑拿到它之后才揭晓自己的。这三步都塞在原来那一问一答里（多一条不用等回话的「揭晓」），用户那边没有多一步。电脑名也算进数字里：用户核对的是「叫 公司Windows 的那台，数字是 123456」，名字被换掉，数字就对不上。

#### 6 位数怎么算（dct-sas-v2）
> **已被替换（2026-09-30）：** 这一节已经被 `2026-09-30-dct-invite-code-design.md`（6 位邀请码 + SPAKE2，dct-invite-v1）替换，代码里已经没有这套流程；下面的原文只留作记录。


字节精确；代码在 `crates/dct-mesh/src/sas.rs`，两边的已知答案向量由一个 Rust 测试（`sas::tests::commit_and_code_match_the_fixed_vectors`）钉着。`field(s)` 是「UTF-8 字节数的十进制 ASCII + `:` + 原始字节」（`crates/dct-mesh/src/canon.rs`）。

1. **加入方 → 邀请方，`Join`**：自签的成员记录，外加 `commit`（标准 base64）。
   - 为问到的**每一台**各出一个 32 字节随机数 `n加入`（不同的电脑不共用）。
   - `rec(m)` = `field(name)` ‖ `field(endpoint)` ‖ `field(sign_pub)` ‖ `field(kx_pub)`（公钥是标准 base64；`added_at` 不算）。
   - `commit` = SHA-256(`field("dct-sas-commit-v2")` ‖ `rec(加入方)` ‖ `field(b64(n加入))`)。
2. **邀请方 → 加入方，`JoinPending`**（`Join` 的答复）：自签的成员记录，外加一个**新出的** 32 字节随机数 `n邀请`（标准 base64）。同一台再请求一次就换一个。这时邀请方还不亮数字。
3. **加入方 → 邀请方，`JoinReveal`**：`n加入`。邀请方验 `commit` 对得上才算数字、亮出来；对不上的整条请求扔掉。一个 `JOIN_TTL`（10 分钟）里最多亮 `MAX_CODES_PER_TTL`（20）个数字，超出的请求直接扔掉。
4. 两边都算：数字 = SHA-256(`field("dct-sas-v2")` ‖ `rec(邀请方)` ‖ `rec(加入方)` ‖ `field(b64(n邀请))` ‖ `field(b64(n加入))`) 的前 4 字节按大端读成 u32，`% 1_000_000`，补零到 6 位。

加入方收到 `JoinPending`（里面有 `n邀请`）之后，先算数字、记下邀请，再揭晓 `n加入`；邀请方在揭晓之前不给用户看这条请求，也批不了。

加入方这一侧也有上限：中转报的在线列表先去重，超过 `MAX_JOIN_ASK`（16）台就一台都不问、一个数字都不给看（`MeshProblem::TooManyAnswered`）。不然中转可以列一大串假电脑、个个名字照抄用户的真电脑，新电脑屏幕上每多一个数字就多一次碰巧对上的机会。

**已知答案向量**（控制端用独立的 Python 实现算出）：

```
邀请方 A：name "A"，endpoint "c-aaaa"，
          sign_pub = b64(0x04 ‖ 64 个 0x01)，kx_pub = b64(32 个 0x02)
加入方 B：name "B"，endpoint "c-bbbb"，
          sign_pub = b64(0x04 ‖ 64 个 0x03)，kx_pub = b64(32 个 0x05)
n邀请 = 32 个 0x11，n加入 = 32 个 0x22

commit(B, n加入) = 1b37730e640d4c4ee0d2b1915492a5c86aa2c67a66525eb3bc50e36983434c50
数字             = 204106
```

旧的 `dct-sas-v1`（数字只看两台的端点和公钥）已经作废；还没有部署过，不需要兼容。

### 踢掉一台电脑

`dct peers remove 公司Windows`，或者在清单里选中它删除。名单重签后，那台电脑发来的信封一律丢弃；它的账号凭据也在中转上作废（**第一步还没做到**：中转令牌要等它自己过期，见「已知限制」第 2 条）。

## 第 2 段：留言

### 地址和清单

- 地址是 `电脑名/会话名`，比如 `公司Windows/dc-terminal`。会话名就是 dct 看板上的名字。
- `dct peers`（MCP 里同名工具）列出组里每台电脑：
  - 在不在线、系统是什么；
  - 开着哪些会话，每个是忙还是闲；
  - 接了哪些触手（iPhone 镜像、摄像头、GPU……），这个信息从 dco 的 `~/.dco/endpoint.json` 读。
- TUI 看板多一栏「我的电脑」，内容和上面一样。
- **怎么知道发给谁**：多数时候用户不用自己挑。用户说「让公司那台跑一下 Windows 测试」，智能体先查清单，按系统和开着的项目找到对应的电脑和会话。只在它拿不准时（比如两台都是 Windows）才问用户。

### 发

- `dct send <地址> "<内容>"`（MCP 里同名工具）。Claude、Codex 等 dct 管的智能体都能调。
- 每条留言都有 id，用发送方电脑的钥匙签名，用收件电脑的加密公钥加密，然后装进中转信封。

### 收

- 收件电脑先验签名，名单里没有的电脑发来的一律丢弃。
- 验过以后，把留言送进目标会话，外面包一层标记：

  ```
  [来自 家里Mac/dc-terminal 的留言 #a1b2]
  ……内容……
  ```

  让那个智能体知道这是另一个智能体说的话，不是用户本人的指令。
- 目标会话**在忙就排队**，等它这一轮结束再送进去，不打断手上的活。忙和闲 dct 本来就知道。
- 送达后回一个「已送达」回执给发件方。

### 对方不在线

中转不存东西（第 0 段第 4 条），所以**留言存在发件方自己的电脑上**：
- 发件方 dct 把没送出去的留言记在 `~/.dct/outbox/`（加密后的信封，0600）；
- 收件电脑一上线（中转报在线）就重发，最多保留 7 天，过期了告诉发件的会话「没送到」；
- 代价：发件电脑也得开着。两台电脑都关机，就得等两台都开机才送得到。

### 权限

- **留言不带执行权。** 它只是送进对方会话里的一段话。对方智能体读了以后做不做、怎么做，照它自己原有的权限规则办。
- 留言要引发对外或动钱的动作，仍然走执行票，要指纹的照样要指纹。这一点不因为消息来自另一台电脑而放松。
- 现在组里只有自己的电脑，互相都能留言。「群」里别人的电脑怎么限权，见第 3 段末尾。

## 第 3 段：派活

派活 = 留言 + 自动回话 + 状态，不另起一套。

- **派**：`dct task <地址> "<要做的事>"`。
  - 地址可以写 `公司Windows/new:claude`，意思是在那台电脑上新开一个 Claude 会话来做。
  - 对方收到一条带任务编号的留言，末尾附一句：「做完用 `dct done <编号> "结果"` 回报」。
- **状态**：派出 → 已送达 → 在做 → 完成 / 失败 / 超时。
  - 「在做」不靠对方主动报，用 dct 已有的忙闲状态；
  - 默认 2 小时没回报标「超时」，并提醒派活的一方。时长可以改。
- **结果**：以留言形式送回派活的会话，内容是「任务 #12 完成：……」。
  - 结果太长时（比如整份测试日志），只送摘要，加一句「全文在 公司Windows 上，要看就 `dct task-result 12`」。拿全文的时候再从那台电脑取。
- **谁能派**：
  - 自己的电脑之间互相都能派；
  - 以后「群」里别人的电脑，默认只能留言、不能派活。派活要群主对某台电脑单独打开，而且可以只开到某个会话。
- **不做**：自动拆活、自动挑最闲的电脑。那是 dct 大脑以后调度的事，这一轮只做「指名派给谁」。

## 看得到什么

- **TUI（开发者）**：
  - 看板上「我的电脑」一栏；

1. **连通自己的电脑**：

## 和之前讨论不一样的地方（写文档时查代码后的修正，请用户确认）

1. **中转还没上线，也没有鉴权。** 讨论时我说过「每台电脑已经连着 dataclue.cn 上的中转，手机就是走这条线」，这是错的：中转从没上过公网，手机走的是 Telegram。所以第 1 步要多做「中转加鉴权并上线」，比讨论时估计的大一些。
2. **第 1 步改回账号登录，不用配对码。** 讨论时为了不等课堂，建议第 1 步先用「老电脑出码、新电脑输码」。查代码后发现 dct 已经有「浏览器里确认登录」的流程，而中转上公网之前必须有账号鉴权（原设计第三条）。与其先做一套配对码再换，不如第 1 步就用账号登录，加上已有电脑的确认。用户早先同意的也是这个办法。
3. **离线留言存在发件方电脑上，不存在中转上。** 讨论时说「中转上加密存 7 天」，这违反原设计「连密文都不落盘」这一条。现在改为：发件方电脑保存，对方上线后重发。
4. **配对核对改成「看两边的 6 位数字」**，代替原设计的当面扫码。原因见第 1 段。

## 已知限制（第一步交付时，2026-09-28）

第一步做完、终审之后仍然成立的限制。**下一步的计划从这里读，不要当它们已经解决了。** 每条写清楚：会怎样、代价多大、打算在哪一步处理。

### 名单和加入

1. **两台老电脑同时批准，名单会分叉。** 两台各自在版本 N 上签出不同的 N+1（各加了一台新电脑），先到的那份被收下，另一份因为版本号没往前走被丢掉。代价：两台电脑看到的组不一样，要有人再批一次才合回来。处理：第二步（名单改成「谁签」只有一个、或者能合并）。
2. **被移出的电脑，中转令牌还能用到过期**（最长 7 天，终审 M2）。第 1 段说的「账号凭据在中转上作废」还没做：`group::remove` 只重签名单。那台电脑在令牌过期前还能：列出同账号有哪些端点在线（`/link/peers`）；不停地发 `Join`，让用户屏幕上反复弹请求（上限 16 条挂着的、10 分钟 20 个数字）；把它手上的旧名单版本往上签一版，推给**错过了移除那一版**的成员（见下一条）。处理：网关和中转加撤销，第二步。
3. **不在线的成员会错过名单变化。** 名单是广播一次，不补发（第一步没有离线留言）。错过移除的成员仍按旧名单把被移出的电脑当成员，而被移出的电脑可以在旧名单上签一版新的推给它，它会收。代价：被移出的电脑在那台上「回来了」。处理：第二步的 outbox / 上线后对齐名单。
4. **两台新电脑可能互相加入。** 每台 `dct login` 之后都有一份只有自己的名单，都会回别人的 `Join`；两台同时 `dct join` 对方，结果说不准。代价：用户得删掉 `~/.dct/mesh` 重来。README 里写了「一台一台来」。处理：第二步。
5. **挂着的加入请求、邀请，守护进程一重启就没了。** 代价：重跑 `dct join`。
6. **6 位数仍然是 6 位数。** 先承诺、再揭晓之后，中转每冒充一次只有一百万分之一的机会；一台邀请方电脑在一个 `JOIN_TTL`（10 分钟）里最多亮 20 个数字，新电脑一次 `dct join` 最多亮 16 个（在线列表超过 16 台就一个都不亮）。反过来，同账号的一台电脑（包括被移出但令牌没过期的，见第 2 条）或者中转，可以用灌请求把这 20 个名额、16 个挂起名额用完，让真的新电脑 10 分钟里加不进来。代价：拒绝服务，不是冒充。处理：第二步随撤销一起看。

### 中转和令牌

7. **令牌过期只在请求开始时查。** 一次在过期前开始的长轮询、`ask`，会一直跑到它自己结束。代价：令牌实际多活不到一个轮询周期。
8. **签名接受高 S 值（ECDSA 可延展）。** 同一条消息、同一把钥匙有两个合法签名。所以签名、令牌**永远不能当 id 或去重键**；留言去重按 `(from, id)`。跟 dct-brain 同一个立场。
9. **手机那一路不能用中转令牌。** `mesh::route(.., None)`：`c-` 以外的端点发来的信封一律不回。手机走中转是以后的事。
10. **续期**：剩不到一天就续，**两次尝试至少隔 10 分钟**（成功也算），失败之后隔 1 小时；令牌已经过期还续失败的（比如睡过了 `exp`、醒来还没联网），1 分钟后再试（终审 M1 和复审之后）。网关哪天把令牌有效期调到十分钟以下，令牌会在两次续期之间过期。
11. **租户共享的 API key 永远 401**，而 401 的文案是「请重新配对 DC 账号」，重新配对同一类 key 没用（终审 M4）。文案是冻结契约，要改得网关先回一个能区分的错误体。

### 留言

12. **正文里的换行是原样敲进去的（LF），真的智能体 CLI 会不会把 LF 当回车提交，没验过**（终审 I3）。`tests/mesh_e2e.rs` 用 `cat` 当智能体，测不出来。要是某个 CLI（Claude Code、Codex……）把 LF 当提交，标记行会单独成一轮，正文变成一条**没有标记**的输入，智能体会把它当用户本人的话——这正是标记要防的事。上线清单第 5 步要人在真机上验；验不过的备用做法是按 profile 用 bracketed paste（`ESC[200~ … ESC[201~`）包住整段再敲。
13. **排着队的留言没有过期时间，守护进程一重启就没了。** 每个会话的队列有上限（50 条）。
14. **回放会让 journal 变长。** 每一封被丢掉的信封（重放、签名不对、过期）记一行 journal，没有限速。同账号的电脑或者中转能靠重放把 journal 撑大；去重表本身有上限，内存不会涨。
15. **发件方时钟差超过 10 分钟、或者留言发出时间早于收件方这次启动，会被静默丢掉**，发件方只看到「没回音」（终审 M3）。
16. **回执、状态里的 `from_session` 是对方原样写的会话名，不是解析后的看板名**（终审 M6）。第一步只拿来显示；第二步 `dct task` 要用它之前得改。
17. **`~/.dco/endpoint.json`（触手清单）没有约定格式，也没有大小上限。** 读的时候只挑认得出的字段、每项洗过截短；一个巨大的文件会被整个读进内存。

### 其它

18. **`Mesh::step` 本身 panic 会留下改到一半的状态**（终审 M7）。锁中毒到处都用 `into_inner` 恢复，今天不出事；第二步 `step` 变大时要再看。

## 附录：网关签中转令牌（冻结的线上契约）

**这一节是契约，不是示意。** 网关（dc_llm 仓）和 dct 分头实现，状态码、字段名、
错误文案以这里为准，两边都不许临场发挥——沿用 `2026-09-02-dct-pair-with-dc-llm-design.md`
「三个接口：冻结的线上契约」那节定下的先例。dct 这半边已经照着实现
（`src/mesh/login.rs`）；网关那半边由 dc_llm 会话接手，**本任务不改 dc_llm 仓库**。

这一步要解的是「待定」一节里已经定下的那句：**中转鉴权不要直接收 LLM 的
`api_key`，凭据要按用途分开，给中转另发一个只能连中转的令牌。** 学生用已有的
device code 流程（上面引用的那份文档）登录 dct，拿到的是网关的 `api_key`——那把
钥匙只认网关。这里定义的接口就是分界线：dct 拿 `api_key` 跟网关换一张中转令牌，
中转自己永远看不到、也不需要认得 `api_key`。

**整套接口挂在 `DC_RELAY_TOKENS_ENABLED`（网关里实际的环境变量名是 `DC_ADMIN_RELAY_TOKENS_ENABLED`，沿用 `DC_ADMIN_` 前缀）下，默认关闭。** 关着的时候直接 404
（不是 403——不存在的功能就该像不存在，同 `DC_ADMIN_PAIRING_ENABLED` 的先例）。

```
POST /admin/api/relay/token
  Authorization: Bearer <学生的 api_key>        ← 只发给网关，永不发给中转
  → {"endpoint": "c-<20 hex>"}
  ← 200 {"token": "<relay token>", "exp": <unix 秒>}
  ← 401 {"error": "invalid_api_key"}
  ← 404  功能开关 DC_ADMIN_RELAY_TOKENS_ENABLED 关着
  ← 400  endpoint 不合法（不是 c- 加 20 位小写十六进制）
```

- **`endpoint`** 是发请求这台电脑自己的中转端点 id，由 `dct_mesh::id::endpoint_for`
  从这台电脑的 P-256 签名公钥算出（`"c-"` 加该公钥 SHA-256 摘要前 20 位十六进制，
  `crates/dct-mesh/src/id.rs`）。dct 自己算出来的值恒合法，400 这条分支是网关对
  输入的防御，不是 dct 正常路径会走到的地方。
- `api_key` **只出现在这一次请求的 `Authorization` 头里**：不进请求体、不进日志、
  也绝不转发给中转——中转往后只看得到这张令牌，看不到 `api_key` 本身。

**这一节到「已知答案向量」为止，字节精确到位——目标是让一个完全不认识
`dct-mesh` 这个 Rust crate 的仓库（比如网关那边用 Python 实现签发）能只靠这几段
文字把令牌签对，不用去读 `relay_token.rs` 的源码。** dct 这半边的等价实现和验证
都在 `crates/dct-mesh/src/relay_token.rs`；最下面那条已知答案向量有一个 Rust
测试钉着（`relay_token::tests::the_appendix_known_answer_vector_is_accepted`），
这几段文字改了、代码没跟着改，或者代码改了、这几段文字没跟着改，这条测试就红。

### 1. 规范签名字节（canonical bytes），精确到位

依次对四个字段做「长度前缀」编码，首尾相接，中间不留分隔符——每个字段自己
的长度前缀已经防住了相邻字段粘连（`crates/dct-mesh/src/canon.rs::field`）：

```
encode(s) = <UTF-8 字节长度的十进制 ASCII>":"<s 的 UTF-8 字节>
bytes(claims) = encode("dct-relay-token-v1")
              + encode(account)
              + encode(endpoint)
              + encode(str(exp))       # exp 先转成十进制字符串再编码，
                                        # 不是把 exp 的数值按二进制写进去
```

**四个字段的顺序固定死**：版本标签、`account`、`endpoint`、`exp`，谁也不能重排。
版本标签是字面量字符串 `"dct-relay-token-v1"`（18 个字节），不是版本号变量。

这几个字段（版本标签、十进制的 account、`c-` 加十六进制的 endpoint、十进制的
exp）全部落在 ASCII 可打印字符集里，所以整条 `bytes(claims)` 本身就是一段可以
当文本打印、复制、逐字符核对的字符串——不需要转 16 进制才能看。

**worked example**（跟下面第 5 节的已知答案向量共用同一组 claims）：

```
account  = "424242"
endpoint = "c-0011223344556677889a"
exp      = 1735689600

bytes(claims) =
  "18:dct-relay-token-v1" + "6:424242" + "22:c-0011223344556677889a" + "10:1735689600"

也就是这一整条、67 个字节、逐字符如下（可以直接复制去跟自己的实现比对）：

18:dct-relay-token-v16:42424222:c-0011223344556677889a10:1735689600
```

### 2. 签名

对上面那串 `bytes(claims)` 做 **P-256（secp256r1）ECDSA，哈希用 SHA-256**（也就是
`ECDSA-SHA256`：先对整条 `bytes(claims)` 算 SHA-256，再对摘要做 ECDSA，不是对
原始字节做别的哈希）。签名编码成 **64 字节的 `r || s`**（`r` 32 字节大端、`s` 32
字节大端，首尾相接，不是 DER），再用**标准 base64（`+`/`/`，带 `=` padding）**
编码成字符串，装进令牌 JSON 的 `sig` 字段。

**Python 的 `cryptography` 库默认吐出的是 DER 编码的签名，必须转换**：

```python
from cryptography.hazmat.primitives.asymmetric.utils import decode_dss_signature

r, s = decode_dss_signature(der_signature)          # der_signature 是 ecdsa.sign() 的返回值
sig64 = r.to_bytes(32, "big") + s.to_bytes(32, "big")
sig_b64 = base64.b64encode(sig64).decode()           # 标准 base64，带 padding
```

反过来，中转/dct 验证从别处收到的签名时也是同一套：先从 64 字节切成两个 32
字节大端整数当 `r`、`s`，要验证就把它们编回 DER（或者直接喂给一个接受 `(r, s)`
元组的验证函数），不能拿 64 字节原始拼接直接当 DER 用。

**ECDSA 签名本身是可延展的（malleable）**：同一条消息、同一把私钥，`(r, s)` 和
`(r, n-s)` 都是合法签名。所以下面已知答案向量里给出的 `sig`／`token` 是**这一次
签出来的一个合法值**，不是唯一合法值——网关那边用 Python 重新签同样的 claims、
同样的私钥，大概率会得到字节不同但同样合法的另一个 `sig`（除非两边都用确定性
nonce，比如 RFC 6979，且实现细节完全一致）。因此第 5 节的向量不是拿来比对「签出
来的字节是否完全相同」，而是拿来确认「用这把公钥去验这个固定的 token，必须通过」
——这才是网关和 dct 双方都要对得上的那件事。

### 3. 令牌字符串

令牌本身是 **`base64url`（不带 padding）** 编码的一段 JSON：

```json
{"account": "<账号标识符，对调用方不透明>", "endpoint": "<c- 加 20 位小写十六进制>", "exp": <整数>, "sig": "<标准 base64，带 padding>"}
```

**JSON 里四个字段的先后顺序不重要**——中转和 dct 验证时验的是第 1 节那串按固定
顺序拼出来的 `bytes(claims)`，不是直接验这段 JSON 的字节，所以序列化库输出的字段
顺序（Python 的 dict 插入序、Rust 的 struct 字段序……)怎么样都不影响验证结果。
`exp` 在 JSON 里是数字，不是字符串——只有喂给第 1 节 `encode()` 的时候才转成
十进制字符串。

### 4. 中转信任的公钥

中转的 `--relay-keys` 文件是一份公钥清单，**一行一把**，每一行是该公钥的
**SEC1 未压缩编码**（65 字节：`0x04` 前缀 + 32 字节 X 坐标 + 32 字节 Y 坐标）用
**标准 base64**（带 padding）编码后的字符串。中转启动时把文件每一行都解码成一把
公钥，验证令牌时依次去试，任一把验过就算数——`relay_token::verify` 的实现已经
是这个形状（`crates/dct-mesh/src/relay_token.rs`），这样网关将来轮换签名钥匙、
同时挂两把，不需要中转和网关同时发版。**这把签名钥匙是网关自己单独一把**，跟每
台电脑各自的身份钥匙（`MachineKeys`）无关，也不需要落在 dct 这边。

### 5. 已知答案向量（Known-Answer Vector）

**下面这把私钥只用于这条向量，任何环境都不许用它签发真令牌**——它的明文写在

**要通过的检查**：`dct-mesh` 的 `relay_token::verify(token, &[issuer_pub], now)`

网关那边（Python 或别的语言）如果要自测「我签的令牌是不是这份契约要的形状」，

dct 侧的对应测试是
`relay_token::tests::the_appendix_known_answer_vector_is_accepted`
（`crates/dct-mesh/src/relay_token.rs`）：拿这份文档里原样抄出来的公钥和 token
调 `verify`，钉住这段文字不会跟代码走岔。

**dct 这边的失败文案**（`mesh::login::fetch_token` 直接返回给学生看的中文，不是
错误码——这个模块今天没有自己的 i18n key，往后接 TUI 时再决定要不要挪过去）：

- 401 → 「登录已失效，请先在 dct 里重新配对 DC 账号」
- 404 → 「服务器还没开放多电脑功能」
- 400 → 「这台电脑的身份码不合法，没法申请多电脑令牌」（正常路径走不到，见上）
- 网络本身连不上（超时、DNS、连接被拒……）→ 「连不上网关，检查一下网络，然后重试」
- 其它状态码 → 「网关出错了（&lt;状态码&gt;），请稍后再试」

**续期**：`mesh::login::needs_renewal(exp, now)` 剩不到 1 天（86400 秒）就返回
true——Task 5 的连接线程按这个信号调 `fetch_token` 续期；续期失败只记一条警告、
继续用旧令牌，不打断已经在跑的连接，旧令牌只要没到 `exp` 仍然有效。两次续期尝试
之间至少隔 10 分钟（不管成没成），失败之后隔 1 小时，令牌已经过期时失败隔 1 分钟（`mesh::login::Renewer`）：网关
哪天发的令牌有效期短于一天，也不会让每台 dct 每一轮轮询都来敲网关。

**落盘**：令牌存 `secrets.toml` 的 `mesh::login::RELAY_TOKEN_KEY`（`"__relay__"`）；
过期时间存旁边的 `mesh::login::RELAY_TOKEN_EXP_KEY`（`"__relay_exp__"`）。两个都是

### 网关实现备注（2026-09-28，dc_llm `d05aff1`）

- `account` 是 dc_llm 的 `User.id`（ULID，形如 `usr_01J...`），对中转和 dct 都是不透明字符串。
- api_key 到 account 的映射：用 `ApiKey.created_by_user_id`。管理员给整个租户开的共享 key 没有单一归属人，返回 401，不拿租户 id 顶替，否则同租户几个人的电脑会落进同一个 account，互相看得见。多电脑第 1 步只连「自己的电脑」，这个行为正确。
- 签名私钥放在环境变量 `DC_ADMIN_RELAY_SIGNING_KEY`（64 位十六进制）。填成第 5 节公开的测试私钥时按值拒签，返回 503。开关开着但没配私钥时也返回 503。
- 公钥用 `python -m scripts.relay_signing_key show` 导出一行，就是中转 `--relay-keys` 文件里的一行。
