# 直播观众链接：一份屏幕，多人只读，学生能提问

日期：2026-09-12
状态：设计已确认，待写实施计划

## 要解决什么

老师上课时想把自己的终端发给学生看。今天做不到：网页端（`src/web`）是一个
token 打通全部路由的双向通道，发给学生等于把终端的写权限一起发出去；而且它是
一个连接一条线程、`MAX_INFLIGHT = 32`，50 人以上直接 503。

目标场景由用户确认：**互联网优先**（学生在家、在别的校区），**50–200 人同时看**，
学生能在老师"上架"的几路里自己选，并且能提问。

## 已确认范围

- 学生只能看，不能操作。这一条不靠权限判断，靠管子的形状。
- 老师显式"上架"若干会话，只有上架的那几路上公网。
- 学生能提问、能看见别人的问题、能点"同问"。
- 老师口头回答；系统只负责收集、排序、标记已答。
- 学生匿名，自填一个显示名。不接 dc_classroom 登录。

不在这一版：音视频、回放录制、学生翻历史、文字回复、私聊、图片、@人、
问题导出、CDN 分发、端到端加密。

## 为什么是"中转缓存一帧"，不是另外两条路

三个候选：

1. **中转缓存一帧，学生只读中转**（采纳）
2. 学生直连老师的守护进程，加只读 token + 路由白名单
3. 学生当普通 `Phone` 端点，走现有的 ask/answer 管子

2 和 3 是被算术淘汰的。方案 2：`MAX_INFLIGHT = 32`、一个连接一条线程、
`Connection: close`，第 33 个学生开始收 503，而且要把老师的机器开到公网上。
方案 3：现有管子是一问一答，200 人每秒几帧全部要穿到守护进程里取屏幕，
老师的电脑要干 200 遍同样的活。

方案 1 的两条决定性好处：

- **守护进程的负担与观众人数无关**（O(1)）。1 个学生和 200 个学生，老师那边推的
  是同一帧。
- **"只读"是管子的形状，不是代码判断**。学生那一侧只有 GET，没有任何路由能把
  字节送回老师的终端。方案 2、3 的只读都依赖"白名单没漏判"，而这个链接要发给
  200 个人。

代价：`dct-srv` 从"只搬信封"多出一个"记住最新一帧"的角色。见下面《对 spec
决定一的两处偏离》。

## 整体形状

```
老师的守护进程                中转 dct-srv                 学生浏览器
  ├ 已有：长轮询收信封 ───────► /link/poll                 （与本功能无关）
  ├ 新增：推帧线程 ──────────► POST /live/frame
  └ 新增：拉问题 ────────────► GET  /live/<id>/questions
                                   │ 按 live-id 存最新一帧 + 问题板
                                   │ 内存、有界、有 TTL
                                   ▼
                               GET  /live/<id>          学生页（另一份 HTML）
                               GET  /live/<id>/frame    画面
                               GET  /live/<id>/board    问题板
                               POST /live/<id>/ask      提问
```

### 不变式

**学生的字节永远不进 PTY。** 提问的回程只到中转的问题板；老师在 dct 自己的
面板里读，不会自动敲进任何会话。老师想把某条问题交给 agent，必须自己复制过去。

这个区别不是形式主义：自动送进去就等于 200 个陌生人能往正在跑的 agent 里
注入文字。

## 身份与凭据

| 谁 | 凭什么 | 能做什么 |
| --- | --- | --- |
| 老师的守护进程 | 已有的配对 token（`EndpointKind::Computer`） | 推帧、拉问题、改问题状态，只限自己那个 live-id |
| 学生 | 链接里那串随机 token（新增 `EndpointKind::Viewer`） | GET 帧与问题板、POST 提问与同问 |

学生那把钥匙不接 dc_classroom 登录（任务 5）。直播链接本来就发给一屋子不确定
的人，再套登录既挡不住转发，又把这个功能钉死在任务 5 后面。

链接形如：

```
https://link.tzspace.cn/live/7f3a2c91#t=<64 位十六进制>
```

token 放在 fragment 里：浏览器不会把 `#` 后面的内容发给服务器，它不进任何一层
访问日志。学生页自己读 `location.hash` 再放进请求头。这跟 `page.html` 现在的
`#t=` 是同一个做法。

认证在路由之前，错的 token 一律 401，连"这个 live 存不存在"都不告诉他 ——
与 `web/mod.rs` 现行规矩一致。

## 中转的存储

### 帧

```
live_id → {
    frame:      Bytes,                 // 已 gzip，中转不压也不解
    etag:       u64,                   // 每换一帧 +1
    updated_at: Instant,
    token_hash: [u8; 32],              // 常数时间比对
    tx:         watch::Sender<u64>,    // 唤醒挂着的学生
}
```

`tokio::sync::watch` 是扇出的关键：200 个学生挂在同一个 sender 上，老师推一帧
唤醒全部，中转这边是一次写、N 次读。

### 问题

```
{ qid, name ≤16 字, text ≤200 字, same: u32, at, answered: bool }
```

排序：同问数多的在上，同问数相同则新的在上，已答的沉底。有界 200 条，满了丢
最旧的。

### 硬边界

| 边界 | 值 | 理由 |
| --- | --- | --- |
| 一帧最大 | 256 KB | 一屏终端 gzip 后 3–5 KB；256 KB 已是"不对劲"的信号 |
| 一台电脑最多几路 | 4 | 够"前端/后端/测试/日志"；不设限等于让一台机器吃光中转内存 |
| 推帧最快 | 2 Hz | 终端不是视频，2 Hz 已快过人读字 |
| 问题板 | 200 条 | 满了丢最旧 |
| 提问限流 | 每 viewer 30 秒一条 | 按 viewer-id + IP 记 |
| 同问 | 每人每条一次 | 按 viewer-id 去重 |
| 停推多久后消失 | 60 秒 | 到点整条 live 连同 token 一起蒸发 |

全部在内存、有界、进程停即没有。这与 spec 那条"不排队、不落盘"不冲突：那条禁
的是替离线的人存东西，而这里存的是老师此刻正在广播的东西 —— 没人看也照推，
没人接也不攒。

## 路由

```
POST   /live/frame                  老师推帧。Computer 身份 + 自己的 live-id。
                                    body = gzip 过的帧。→ 200 / 401 / 413 / 429
DELETE /live/<id>                   老师停播。→ 204 / 401
GET    /live/<id>/questions         老师拉问题。→ 200 / 304 / 401
PATCH  /live/<id>/questions/<qid>   标已答 / 隐藏。→ 200 / 401 / 404

GET    /live/<id>                   学生页本体
GET    /live/<id>/frame             学生拉帧
GET    /live/<id>/board             学生拉问题板
POST   /live/<id>/ask               提问。→ 201 / 401 / 413 / 429
POST   /live/<id>/ask/<qid>/same    同问。→ 200 / 401 / 404 / 429
```

读的那几条共用同一套机制：`If-None-Match` 命中回 304；带 `?wait=1` 时挂最多
25 秒，内容一变立刻返回，超时也回 304。

`?wait=1` 是带宽那三条里最管用的：老师手停着不动的几十秒里，200 个学生一个
字节都不传，而画面一变全体在 25 ms 内亮起来。普通轮询那条路留着，作为 `wait`
被中间代理掐掉时的退路。

### 带宽估算

一屏 span JSON 约 20–60 KB。200 人 × 1 Hz × 30 KB ≈ 48 Mbps，中转扛不住。
三条叠加之后：帧不变不推（终端大多数时候是静止的）+ gzip（30 KB → 3–5 KB）+
304/长轮询。讲课时约 1 MB/s，安静时接近零。

## 老师那一侧

### 协议

```rust
Request::LiveStart { ids: Vec<u32>, names: Vec<String> }
Request::LiveStop
Request::LiveStatus
Request::LiveQuestions
Request::LiveMark { qid: String, answered: bool }
Request::LiveHide { qid: String }
Response::Live(LiveInfo)   // { id, token, url, staged, viewers, questions }
```

`PROTOCOL_VERSION: 13 → 14`。新增 `Request` 变体那条规矩没有例外可讲 ——
旧守护进程收到 `LiveStart` 只会回一句解析失败，而用户看到的是"按了开关什么都
没发生"。

### 学生看到的名字是老师起的

`names` 与 `ids` 并排走就是为了这件事：默认 `第 1 路` / `第 2 路`，老师可改成
`后端调试`。**会话标题和项目路径一个字都不上公网** —— 泄密面不靠"学生页不
显示"，靠中转上根本没有那份数据。

### 推帧线程

一条新线程，绝不进那个 200 ms 的 tick（`link.rs` 立的规矩：那条线程卡一下，
所有会话的画面一起卡）。循环四步：

1. 用现成的 `Request::Screens { ids }` 一次取全部上架会话的屏幕
2. 序列化成帧、哈希、与上一帧比
3. 一样就不推
4. 变了就 gzip、`POST /live/frame`

最快 2 Hz，两侧共用同一个常量。另有 20 秒一次的保活推送：中转是 60 秒 TTL，
不保活的话，老师盯着屏幕想一分钟事情，直播自己就没了。

### 停播有两条路

主动：`LiveStop` → `DELETE /live/<id>` → 中转当场丢掉帧、问题和 token，挂着的
学生收 404，页面显示"这场直播结束了"。

兜底：60 秒 TTL，覆盖合上笔记本、断网、守护进程被杀。

两条都必须在。只有 TTL，停播之后学生还能再看一分钟；只有主动删，拔网线就等于
永远播着。

## 学生页

### 它是另一份文件，不是 `page.html` 加开关

开关那种做法会把"学生不能打字"变成一处 `if`，而这一页上"能不能送东西出去"现在
有十几个调用点（输入框、虚拟键行、粘滞 Ctrl、捕获键盘、三个翻历史按钮、
滚轮……）。漏判一个，学生就能往老师终端里敲字，而这件事老师在自己机器上永远
试不出来。

另一份文件能被机器证明：守卫直接对着学生页那份字节断言，里面不许出现
`/api/input`、`/api/key`、`/api/mouse`、`/api/scroll`、`wire.key`、`wire.input`、
`<input`、`<textarea`（提问框除外，见下）。

### 渲染只能有一份实现

```
crates/dct-page/
  shared.js     paint / fitFont / cellSize / 配色 / 主题三档
  page.html     老师那页，带 <!--SHARED-->
  live.html     学生那页，带 <!--SHARED-->
  src/lib.rs    把 shared.js 填进两个占位符，各缓存一份
```

`PAGE` 常量变成 `page()` / `live_page()`（`OnceLock` 拼一次）。这个 crate 现在
没有依赖，拆完仍然没有依赖 —— `OnceLock` 是 std 的。

这是本功能唯一要动的既有结构，服务于当前目标：两页共用渲染，同时让"学生页里
没有输入路径"成为文件级事实。

### 学生页上有什么

上架的那几路（老师起的名字）、画面、字号 +/− 与主题三档（纯本地，不发请求）、
问题板、一个提问框，以及三种状态说清楚：正在播 / 老师暂停了（60 秒没新帧）/
这场直播结束了（404）。

上面那条守卫因此要精确成：学生页里**除了提问框那一个 `<textarea>` 之外**没有
输入控件，且不存在任何指向会话的写路径。

### 学生页上没有什么

虚拟键行、Ctrl 粘滞、捕获模式、翻历史按钮、滚轮路由、点一行抄进输入框、
会话列表、上传面板。

滚轮只滚学生自己收到的这一屏（浏览器原生），不存在 `/api/scroll`。学生想看
十分钟前的代码 —— 看不了。往回翻要么让学生页存历史（内存爆），要么让学生能
驱动老师的守护进程（回程就出现了）。直播就是直播。

### 提问板的渲染

一律走 `textContent`，不走 `innerHTML` —— 与现有 `paint()` 同一个做法。问题板
是公开的，200 个陌生人能往里写字，这一条没有商量余地。

显示名与 viewer-id 存在学生自己浏览器的 `localStorage` 里。viewer-id 不是身份，
只用于限流和同问去重。显示名不校验，不能当身份用。

## 最危险的失败模式：老师忘了自己在播

不是链接泄露，是老师切去处理一件私事而某一路还在播。四道防线，第一道最重要：

1. **TUI 顶栏常驻一行**：`● 正在直播 · 2 路 · 7 人在看 · 3 个新问题`。与
   `scroll_hint` 同级的显眼位置，不能折叠、不能关掉。
2. **人数是实时的**（中转数挂着的订阅数，随帧返回）。"7 人在看"比任何提示语
   都有效。
3. **守护进程一退就停播。**
4. **上架是按会话的白名单** —— 老师切到别的会话，播的仍然是上架那几路，
   切屏本身泄不了密。

## 链接发出去就收不回来

学生把链接转到群里拦不住，任何鉴权都拦不住。设计上不假装能拦，只保证能作废：

- 停播即失效（token 与帧、问题一起消失）
- 一键换链接：生成新的 live-id 与 token，旧的当场死掉；上节课的链接这节课打不开

## 对 spec 决定一的两处偏离

原文是"中转只搬信封，不看里面"。这里有两处要正面交代：

**第一处：中转记住最新一帧。** 多出来的是一个角色，不是一份理解 —— 帧对中转
仍然是 `application/octet-stream` 的不透明字节，它不解析、不认识里面是 span
还是别的。守卫照抄现成的 `the_relay_never_looks_inside_the_payload`：`dct-srv`
里不许出现 `ScreenSpan`、`Response`、`from_slice::<Request>` 这些名字。

**第二处：问题板它确实"看"了** —— 要存字段、数同问、排序。能接受的理由和边界：
**这是中转自己的数据模型，不是 dct 的协议。** 中转仍然不认识 `Request` /
`Response`；问题板是中转自己的一件东西，而信封永远只是它搬的货。

将来有人想让中转"顺手解析一下帧"时，要能从这两段读出线画在哪儿。

## 部署上的真依赖

`crates/dct-srv/src/main.rs` 现在硬拒绑非环回地址，理由是 `/link/*` 那几条
没人验 token（接 dc_classroom 是任务 5），加密是第二期。

本功能不需要等任务 5，但**部署形态要写死**：公网上只放行 `/live/*`（它自带
鉴权），`/link/*` 继续只听本机。反向代理上一条路径白名单的事，但它必须写进
部署文档，不能靠谁记得。

**这是本功能唯一的外部依赖，也是唯一能把它做砸的地方**：哪天有人图省事把整个
中转开到公网上，配对那条链路就裸奔了。

端到端加密（第二期）不是本功能的前置条件：直播的收件人本来就是一屋子陌生人，
TLS 到中转是这个场景正确的安全模型，不是妥协。

## 测试

**中转**：帧的存取、ETag/304、长轮询被新帧唤醒、TTL 到期蒸发、429、413、
4 路上限、错 token 回 401 且不泄露 live 是否存在、提问限流、同问去重、
问题板有界丢最旧、payload 仍然不透明。

**学生页**：那份字节里不许有会话写路径（上面那张清单），除提问框外没有输入
控件。

**共享渲染**：现在那条"等宽字体名只许出现一次"推广到两页合起来看。

**推帧线程**：假中转（`link.rs` 的 `FakeSrv` 现成可抄）—— 画面不变时不推、
20 秒保活照推、`LiveStop` 真的发了 DELETE。

**协议**：`PROTOCOL_VERSION` 14，钉死线上形状的那条测试同步更新。

**手工验收**：照 `serve_for_a_manual_look` 再做一个脚手架，起中转 + 学生页，
用眼睛看。
