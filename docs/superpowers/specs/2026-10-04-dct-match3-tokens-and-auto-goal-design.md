# dct 玩三消：记录大模型用了多少 token，自动认出目标数字（第五轮）

日期：2026-10-04
前提：第三轮（问网关大模型）和第四轮（通用反馈：停滞检测、进度数字）已合入 main 并推送。第四轮留下两个缺口，这一轮补上：

1. 不知道每次问大模型花了多少 token，所以「省了多少」只是估计。
2. 停滞检测要用户手动给 `--goal-number`；用户（零编程经验）不会知道屏幕上第几个数字是目标。

## 原则

dct 只放通用代码。本轮两件事都满足「换一个别的方格游戏还成立吗」：token 是模型的事，和游戏无关；「每走成功一步就刚好降 1 的那个数是步数」对所有有步数限制的游戏都成立。

## 一、记录大模型用了多少 token

### 做什么

- `llm::Backend` 加一个**带用量的调用** `complete_counted(&self, p) -> Result<(String, Option<Usage>), LlmError>`，默认实现调 `complete` 返回 `None`（所以 `CliBackend` 和所有现有后端不用改）。`Usage { input: u64, output: u64 }`。
- `HttpBackend` 重写它：从响应体读用量。OpenAI 型：`usage.prompt_tokens` / `usage.completion_tokens`；Anthropic 型：`usage.input_tokens` / `usage.output_tokens`。任一字段缺失或不是数字 → 整个 `Usage` 是 `None`，不报错（不能因为读不到用量就丢掉一个好答案）。
- `complete_with_timeout` 不动；新增 `complete_counted_with_timeout`，同样的线程和超时办法。
- `dct-game` 的 `Advice` 加 `tokens: Option<(u64, u64)>`（输入、输出）。`LlmAdvisor::pick` 用带用量的调用，填进去。
- 记录里的 `ask` 对象多两个字段：`tokens_in`、`tokens_out`（读不到就是 `null`）。
- `LlmAdvisor` 内部用原子计数累计这一次命令的总次数和总 token；`dct game play` 结束时，**如果问过模型**，打印一句大白话：「这次问了大模型 N 次，一共用了约 X 个字（输入 A，输出 B）。」读不到用量时只说次数：「这次问了大模型 N 次（没有读到用量）。」没问过就不打印。

### 不做

- 不按钱换算（价格会变，也不在 dct 里）。
- 不估算图像的 token（dct 不送图）。
- 不改 `CliBackend` 去解析各家 CLI 的用量输出。

## 二、自动认出目标数字

### 要解决什么

第四轮的停滞检测只有在用户给了 `--goal-number N` 时才工作。屏幕顶部读出来的数字有：剩余步数（每成功一步降 1）、目标数（降得不规律）、有时还有分数（只增不减）。不给 N 时，应该由 dct 自己判断哪个是目标。

### 做法（全部只看数字的变化，不看数字的意思）

`play()` 在每个**成功走了一步**（`moved`，不含被拒绝的）之后，已经有 `progress.before` 和 `progress.after` 两份数字列表。对「前后个数相同」的那些步，按下标记录每个数字的变化量。

一个下标满足下面某一条，就被**排除**：
- 它是**步数**：到目前为止每次变化量都刚好是 −1，且至少 4 个样本；
- 它**增加过**（分数、连击这类）；
- 它**从未变过且样本不到 4 个**时先不下结论（不排除也不选）。

在至少 4 个样本之后，如果**排除后恰好剩下一个下标**，它就是目标；多于一个或一个都没有，就**不判断**（和现在不给 `--goal-number` 时一样：不判停滞、不因停滞问模型）。用户给了 `--goal-number` 时，一律用用户的，不自动认。

认出来以后：
- 记录里在每一步的 `progress` 里多一个字段 `goal_index`（0 起；还没认出就是 `null`），用户能从日志看到它认成了哪个；
- 停滞计数从认出的那一步之后开始算（不追溯）；
- 第一次认出时打印一句大白话：「我认为屏幕上第 N 个数字是这一关的目标。」

目标认错的代价：停滞判断会不准，只会多问或少问一次模型，不会划出不合规的步。认错了用户可以用 `--goal-number` 覆盖。

### 不做

- 不读数字旁边的文字或图标来判断它是什么（那是游戏专属，也要看图）；
- 不跨关卡记忆（每一次 `play()` 重新认；`--auto-next` 换关时也重新认）；
- 不处理「目标数字中途变成对勾」这类（数字个数变了，这一步就算「未知」，已有的规则）。

## 测试

- Token：假后端分别返回 OpenAI 型、Anthropic 型的响应体，用量读对；缺字段/非数字/没有 `usage` → `None` 且答案照样返回；`complete_counted` 默认实现返回 `None` 且结果和 `complete` 一样；`Advice.tokens` 带到记录的 `ask.tokens_in/out`；结束语的三种说法（用量齐、没读到用量、没问过）。
- 自动认目标：
  - 步数 −1 每步、目标每步降不同数 → 认出目标，步数被排除；
  - 分数只增、目标降 → 认出目标；
  - 目标始终不动、步数每步 −1、分数增 → 排除步数和分数，恰剩一个（目标）→ 认出，之后判停滞；
  - 两个都变化不规律 → 不判断；
  - 样本不足 4 个 → 不判断；
  - 个数不同的步不进样本；
  - 用户给了 `--goal-number` 时不自动认，且日志里 `goal_index` 是用户的那个。
- 变异测试照老规矩：步数判定的「刚好 −1」、「至少 4 个样本」、「恰剩一个」。

## 验收（真机，需要用户在场）

1. 第 1716 关这类有步数和目标的关：不给 `--goal-number`，10 步内日志里 `goal_index` 指向目标那个数字（我对着屏幕核对）；
2. 用 `--ask-every-step` 玩几步：结束时打印问了几次、用了多少 token；记录里每条 `ask` 有 `tokens_in/out`；
3. 网关读不到用量时（换一个不返回 `usage` 的模型或断开）：不崩，说「没有读到用量」。

## 已知的限制

- 只有 HTTP 后端读得到用量；走命令行的后端读不到。
- 目标数字自动认出需要 4 步以上的样本，开局几步判断不了。
- 若某一关目标数字在前几步恰好每步也降 1，会被当成步数排除（极少见）。
