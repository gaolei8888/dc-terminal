# dc-terminal 产品改进与自动化开发方案

**面向 Claude Code、Codex 与 dc_llm 的持续开发执行平台**

> **核心愿景**
> 不是让用户在任何地方继续操作终端，而是让软件开发持续自动推进；用户无论身处何地，只需提出目标、处理关键决策并验收成果。

**版本：** V1.0  
**日期：** 2026年8月

# 一、执行摘要

dc-terminal 当前已经具备多 Agent 会话、后台持续运行、项目切换和基于 Git 的自动快照等基础能力。下一阶段不应继续围绕“支持更多模型”进行横向扩展，而应把产品从终端会话管理器升级为任务驱动、可远程监督、可自动验证的软件开发执行平台。

建议以 dc_llm 作为常驻的轻量支持与调度层，以 dc-terminal 作为开发任务运行时，以 Claude Code、Codex 等前沿代码 Agent 作为重型执行引擎，并与 dc-workspace 的需求、项目和企业协作能力形成清晰分工。

> **一句话定位**
> dc-terminal 让 Claude Code 和 Codex 在后台持续完成开发；dc_llm 负责理解、调度、状态判断和远程交互；用户可以随时随地提交任务、参与决策并验收成果。

## 核心改进方向

- 从“管理 Session”转为“管理开发任务”。
- 从“远程看终端”转为“远程处理目标、决策和验收”。
- 从“Agent 修改代码”转为“自动完成理解、开发、测试、修复和交付”。
- 从“单机工具”转为“可运行在个人设备、公司服务器和云端开发机上的持续服务”。
- 以 dc_llm 承担低成本常驻支持，避免所有状态判断和交互都调用昂贵前沿模型。

# 二、产品定位与边界

## 2.1 当前产品的真实位置

dc-terminal 不是新的代码模型，也不应被定义成 Claude Code 或 Codex 的替代品。它更适合成为代码 Agent 的统一运行、监督、隔离和恢复层。Claude Code、Codex 越强，dc-terminal 的交付能力越强。

| **层级**            | **主要职责**                                         | **不应承担的职责**             |
|---------------------|------------------------------------------------------|--------------------------------|
| dc-workspace        | 需求、客户、项目、团队、知识和企业协作               | 直接管理 PTY 或代码执行细节    |
| dc_llm              | 持续理解、任务路由、状态判断、摘要、通知与上下文保持 | 替代复杂代码开发模型           |
| dc-terminal         | 任务运行、工作区隔离、Agent 调度、测试、恢复与交付   | 自己训练基础代码模型           |
| Claude Code / Codex | 复杂代码分析、修改、测试与重构                       | 承担企业项目治理和长期状态管理 |

## 2.2 新的产品主张

> **主张一**
> 开发环境持续工作，用户只管理目标、决定和结果。

> **主张二**
> 用户不需要在任何地方“写代码”，而可以在任何地方推动软件持续完成。

> **主张三**
> dc_llm 始终在线，Claude Code 和 Codex 在需要时完成高强度开发。

# 三、目标产品架构

建议采用“控制面—支持层—执行层—基础能力层”的四层结构。

| **控制面：dc-workspace / Web / 手机 / 企业微信 / 飞书** | 创建任务、查看项目、处理审批、验收成果、管理团队和客户。                                                           |
|---------------------------------------------------------|--------------------------------------------------------------------------------------------------------------------|
| **支持层：dc_llm**                                      | 把自然语言需求整理为任务；选择 Agent；持续读取状态；识别卡住、等待和完成；生成通知与决策卡片；维护轻量任务上下文。 |
| **执行层：dc-terminal**                                 | 创建独立工作区；启动和监督 Agent；执行测试、构建、安全检查；保存日志和检查点；合并或放弃改动。                     |
| **能力层：Claude Code / Codex / OpenCode / 项目工具链** | 完成代码分析、实现、调试、测试、重构及特定工具调用。                                                               |

## 3.1 dc_llm 的核心职责

- 任务理解：把用户的一句话需求整理为目标、范围、限制条件和验收标准。
- Agent 路由：根据任务类型、项目语言、成本和上下文选择 Claude Code、Codex 或其他执行器。
- 状态感知：从终端输出、工具调用、Git 变化和测试结果中识别当前阶段。
- 轻量交互：回答“现在做到哪里”“是否卡住”“需要我做什么”等高频问题。
- 上下文压缩：把长日志和历史执行过程压缩成可供新 Agent 恢复的任务状态。
- 通知生成：把技术细节转换为手机可读的决策卡片、风险提示和完成报告。
- 成本控制：将简单判断和摘要留在小模型，仅在复杂代码任务中调用前沿 Agent。

# 四、用户体验重构：从会话到任务

## 4.1 任务成为第一等对象

用户不应首先选择 Session、PTY 或 Agent，而应首先表达“要完成什么”。任务名称、目标、项目、状态、验收标准和结果应成为主界面的核心信息；Agent 类型只作为次要执行信息展示。

| **提交目标** | **自动理解** | **选择执行器** | **独立执行** | **自动验证** | **用户验收** |
|--------------|--------------|----------------|--------------|--------------|--------------|

## 4.2 推荐的新建任务体验

1.  选择或自动识别项目。
2.  输入一句自然语言需求，例如“修复移动端登录后白屏”。
3.  dc_llm 自动生成任务名称、目标范围和建议验收条件。
4.  系统自动推荐 Claude Code 或 Codex；高级用户可手动调整。
5.  dc-terminal 自动创建独立 worktree、分支和运行环境。
6.  用户确认后开始，后续仅在关键决策和完成时收到通知。

## 4.3 更有意义的状态体系

| **内部状态** | **用户看到的状态**                            | **用户真正关心的问题**   |
|--------------|-----------------------------------------------|--------------------------|
| working      | 正在理解需求 / 检查代码 / 修改文件 / 运行测试 | 现在正在做什么？         |
| asking       | 等待你决定                                    | 需要我做什么？           |
| blocked      | 可能卡住 / 测试重复失败                       | 是否需要暂停或改变方案？ |
| done         | 已完成，等待验收                              | 改了什么、验证是否通过？ |
| failed       | 执行失败，可恢复                              | 能否重试、从哪里继续？   |

# 五、充分的开发自动化闭环

产品目标不是让 Agent 只完成一次代码修改，而是自动执行完整的软件工程过程，并在达到项目定义的完成标准后才进入验收。

| **理解需求** | **分析代码** | **制定计划** | **实现修改** | **编写测试** | **运行验证** | **自动修复** | **生成交付** |
|--------------|--------------|--------------|--------------|--------------|--------------|--------------|--------------|

## 5.1 自动化执行内容

- 自动识别技术栈、入口模块、测试方式和构建命令。
- 自动建立独立 Git worktree、任务分支、端口和必要的运行隔离。
- 自动保存阶段检查点，而不是仅在每轮对话前保存模糊快照。
- 自动运行单元测试、构建、Lint、类型检查和项目自定义验收脚本。
- 测试失败后允许 Agent 在限定轮次内自动分析和修复。
- 自动生成代码变更摘要、测试结果、风险说明和必要的预览地址。
- 用户接受后自动提交、合并或创建 Pull Request；放弃后清理任务环境。

## 5.2 项目级完成标准

每个项目应拥有可配置的 Definition of Done，并由系统在任务完成前自动验证。配置界面应优先使用向导，TOML/YAML 仅作为高级入口。

> **示例：**
> - 单元测试必须通过
> - 构建必须成功
> - 不允许修改 .env 和 production/
> - 数据库迁移必须提供回滚
> - 前端任务必须生成可访问预览

# 六、随时随地开发的交互体系

“任何地方、任何场合进行开发”不应等同于在手机上复刻终端。移动体验的核心是以最少的信息完成任务发起、关键决策和最终验收。

## 6.1 多入口统一任务系统

| **入口**                   | **适合操作**                       | **不建议承载**        |
|----------------------------|------------------------------------|-----------------------|
| 桌面 TUI                   | 完整终端、实时日志、Diff、深度调试 | 企业项目管理          |
| Web 控制台                 | 任务看板、详情、验收、团队协作     | 完整 IDE 替代         |
| 手机 App / H5              | 提交任务、处理决定、查看完成报告   | 长时间阅读终端日志    |
| 企业微信 / 飞书 / Telegram | 通知、选项决策、快速补充要求       | 复杂配置和大规模 Diff |

## 6.2 手机端只做好四件事

1. 创建或补充任务
2. 回答 Agent 的关键问题
3. 处理异常和风险提醒
4. 验收、继续修改或放弃成果

> **设计原则**
> 手机端是开发任务的遥控器和审批中心，不是缩小版 IDE。

# 七、安全、隔离与可恢复性

基于 Git 的隐藏快照只能恢复项目文件，不能恢复数据库、云资源、项目目录外文件或已经发生的网络操作。因此，快照应被视为基础体验能力，而不是完整安全方案。

## 7.1 建议的安全组合

- 每个任务使用独立 worktree 和任务分支，避免同一项目的多个 Agent 相互覆盖。
- 高风险任务运行在容器、沙箱或受限用户中，限制文件系统、网络和系统命令。
- 为 .env、密钥目录、生产配置和基础设施脚本设置保护规则。
- 数据库和云资源操作默认需要显式批准，并生成操作计划与回滚说明。
- 完整记录用户指令、Agent 操作、命令输出、文件变化和审批过程。
- 在可逆阶段建立检查点，在不可逆动作前建立人工门禁。

## 7.2 卡住检测与自动恢复

- 连续多次执行同一命令或出现相同错误时，标记“可能卡住”。
- 长时间无输出且无文件变化时，询问 Agent 当前计划或自动暂停。
- 上下文接近上限时，由 dc_llm 生成任务状态摘要并重新启动执行器。
- Agent 崩溃、网络中断或主机重启后，从最近阶段检查点继续。
- 自动重试必须设置轮次、成本和时间上限，避免无限循环。

# 八、关键产品页面建议

## 8.1 任务收件箱

首页应按照“需要用户处理”的优先级组织，而不是简单罗列所有 Session。

> **推荐排序**
> 等待用户决定 → 出错或卡住 → 已完成待验收 → 正在执行 → 已接受/已放弃。

## 8.2 任务详情页

- 目标与验收标准；
- 当前阶段与最近活动；
- 已修改文件和核心变更摘要；
- 测试、构建和安全检查结果；
- 执行日志与完整终端入口；
- 接受、继续修改、暂停、恢复和放弃操作。

## 8.3 完成交付卡片

> **任务已完成**
> 实现内容：修复登录状态恢复与路由初始化之间的竞争问题。 代码改动：修改 3 个文件，新增 1 个回归测试。 验证结果：单元测试与构建通过；尚未进行生产环境验证。 操作：接受并合并 / 继续修改 / 查看详情 / 放弃改动。

# 九、功能优先级与实施路线

| **阶段**          | **重点能力**                                       | **核心交付**                         | **成功标志**                            |
|-------------------|----------------------------------------------------|--------------------------------------|-----------------------------------------|
| P0：任务化基础    | 任务对象、项目识别、Agent 推荐、状态阶段、完成卡片 | 用户可以一句话创建任务并看到清晰结果 | 不需要理解 Session/PTY 即可完成首次任务 |
| P0：安全并行      | 独立 worktree、任务分支、接受/放弃闭环             | 同一项目多个任务可安全并行           | 任务间无文件覆盖，成果可一键合并或清理  |
| P1：dc_llm 支持层 | 状态识别、摘要、卡住检测、任务恢复上下文           | 低成本常驻理解和通知服务             | 大多数状态查询无需调用前沿 Agent        |
| P1：远程交互      | Web/手机看板、通知、ask_human、验收操作            | 用户离开电脑后任务仍可推进           | 关键问题可在手机上数秒内处理            |
| P2：自动验证      | 项目完成标准、测试构建、安全检查、预览环境         | 从代码修改升级为自动交付             | 多数常见任务可自动达到待验收状态        |
| P3：企业化        | 团队权限、审计、成本、私有部署、GitLab/CI 集成     | 面向企业的开发执行平台               | 可管理多人、多项目和合规要求            |

# 十、产品验收指标

建议避免只统计支持多少 Agent、创建多少 Session，而应重点衡量任务完成质量和用户参与成本。

- 首次成功任务时间：新用户从安装到完成第一个任务所需时间。
- 无人值守比例：无需人工持续关注即可进入待验收状态的任务占比。
- 人工中断次数：每个任务需要用户回答或接管的平均次数。
- 自动验证通过率：完成任务中测试、构建和项目规则全部通过的比例。
- 恢复成功率：Agent 崩溃、网络中断或重启后能够继续的比例。
- 验收一次通过率：用户第一次查看成果即接受的任务比例。
- dc_llm 分流率：由小模型完成的状态、摘要和路由请求占比。
- 单位任务成本：不同任务类型的模型、运行和基础设施平均成本。

# 十一、主要风险与应对

| **风险**         | **表现**                               | **建议应对**                                                     |
|------------------|----------------------------------------|------------------------------------------------------------------|
| 产品过度复杂     | 同时建设 TUI、Web、手机、IM 和企业平台 | 统一任务后端，前端按阶段逐步增加；先做好任务闭环。               |
| 小模型判断不可靠 | 错误识别状态或错误路由 Agent           | 规则、日志信号与 dc_llm 结合；高风险结论交由前沿模型或用户确认。 |
| 自动化失控       | 重复尝试、消耗 Token、执行危险操作     | 设置预算、轮次、命令权限和不可逆操作门禁。                       |
| 远程暴露风险     | 开发主机或终端服务暴露到公网           | 采用反向连接、设备认证、短期令牌、端到端加密和最小权限。         |
| 用户不信任结果   | 只看到“完成”，无法判断代码质量         | 提供验证报告、Diff 摘要、预览、风险说明和可恢复机制。            |

# 十二、最终建议

dc-terminal 最有潜力的方向，不是成为功能更多的 tmux，也不是成为另一个通用桌面 Agent，而是形成一个由 dc_llm 常驻支持、由 Claude Code 与 Codex 执行复杂工作、能够在后台持续推进并接受远程监督的软件开发自动化平台。

> **产品核心原则**
> 不要要求用户管理 Agent；让用户只管理目标、决定和结果。

建议下一版本优先完成三个闭环：

1. 一句话创建任务，并自动形成项目、执行器和验收标准。
2. 独立 worktree 中执行开发、测试和构建，并生成完成卡片。
3. 通过 dc_llm 在 Web 或手机端提供状态摘要、关键决策与验收操作。

当这三个闭环稳定后，再扩展企业协作、私有部署、团队权限和多项目治理。这样可以让 dc-terminal 从一个有特色的终端工具，真正演进为“随时随地推动软件持续完成”的开发基础设施。
