# Encrypted offsite classroom backups

These tools are prepared for operator review. Nothing is installed or scheduled automatically. No command stops or restarts student containers.

The archive includes `/var/lib/dcw-classroom` (account mappings, tokens, audit, administrator password file if present) and Docker persistent volumes. Managed containers must have both `dcw.classroom=1` and matching `dcw.student=<32hex>` labels, exact names and expected mounts. Managed volume names and labels are checked, including retained volumes after a container is removed. The **only** legacy allowlist is `dcw_dct-state`, `dcw_claude-state`, `dcw_work`, confirmed on the current source. A missing expected legacy volume fails export. Arbitrarily labeled database volumes and bind mounts are excluded. Docker's ordinary `/var/lib/docker/volumes` layout is required; alternate volume drivers/mount options fail closed.

Agent state can contain provider credentials, OAuth tokens and private student work. Encryption is mandatory: OpenSSL CMS **AES-256-GCM authenticated encryption**, with a public recipient certificate on the source and the private key kept offline. OpenSSL and Python are already installed on both servers; read-only synthetic public-certificate probes verified CMS AES-256-GCM support on each host. The receiver and relay store ciphertext only. Source plaintext temporary files are private (0700 directory, 0600 files via umask) and removed normally, but a crash/kill or storage remanence can leave recoverable data. Prefer encrypted source storage; do not promise secure erasure. Source root can already read all source credentials.

This is a checked **live file copy**, not an application-consistent snapshot. Unix sockets are omitted. Every other tar warning/error that yields nonzero is fatal, including `file changed as we read it`; metadata inventories before/after detect added, removed and changed files. Docker discovery is repeated before encryption to reject changed volume topology. There is no fallback to `--ignore-failed-read`. A passing run still cannot guarantee cross-file transaction consistency. Schedule a quiet time, alert on failure, and use an approved filesystem snapshot/quiesce design if stronger consistency is needed. No automated retry should claim an earlier failed run succeeded.

## Read-only prerequisite findings (2026-09-11)

- Source `root@dataclue.cn`: GNU tar 1.35, OpenSSL 3.0.13, Docker and Python3. Manager `classroom.json` is root-owned 0600. Current shared container has exactly the three legacy mounts above.
- Receiver `dev@ai.tzspace.cn`: OpenSSL 3.0.2, Python 3.10.12, roughly 506 GiB free; dev home mode 0750. Backup subdirectory must be owned by dev and mode 0700.
- Local SSH to both hosts succeeds. Source-to-receiver SSH fails host-key verification, so `relay.py` deliberately uses the already trusted operator machine to contact each host. Do not disable host-key checks. A source-side timer would first need separately approved pinned host-key verification and dedicated restricted credentials.

## Exact installation proposal — review before execution

1. On an **offline restore machine**, generate a strong encrypted RSA private key and recipient certificate. Keep two protected offline copies and record the certificate fingerprint. Example: `umask 077; openssl req -x509 -newkey rsa:3072 -sha256 -days 3650 -subj '/CN=DCT Backup Restore/' -keyout restore.key -out recipient.crt`. Enter a passphrase interactively. Never upload `restore.key` to either server or commit it. Test recovery of a synthetic archive before using the key for real data.
2. On source, create root-owned `/opt/dct-backup` and `/etc/dct-backup` mode 0700. Install `export.py` into `/opt/dct-backup/export.py` mode 0700 and **only** the public certificate into `/etc/dct-backup/recipient.crt` mode 0600. Verify the fingerprint against the offline record. Allow temporary space for one uncompressed tar plus ciphertext plus final ciphertext; fail if disk is insufficient. A successful export has no compression (predictable CPU use).
3. On receiver, as dev create `/home/dev/dct-backup-tools` and `/home/dev/dct-backups` mode 0700. Install `receive.py` into the tools directory mode 0700. No private key is required. Default retention keeps newest 14 complete `dct-backup-<UTC timestamp>-<16hex>.cms` regular owned files; only this exact namespace is pruned, never symlinks, directories or unrelated names. Transfer limit is 100 GiB per archive; increase only after a capacity review.
4. On the approved operator machine, install/run `relay.py` with Python3 and existing pinned SSH trust. It creates encrypted source output, fetches ciphertext into a private temporary directory, checks SHA-256 during receiver upload and receives acknowledgment, then deletes **only** its exact freshly generated source ciphertext. Receiver stages to a private temporary file, fsyncs and atomically publishes without overwriting an existing backup. On transfer failure the encrypted source file remains for manual retry and the script exits nonzero.
5. Review a first real run and an isolated restore **before scheduling**. Recommended timer runs on an always-on approved operator/backup host, daily at a quiet hour; alert on nonzero exit and missing successful run within 26 hours. No timer or cron file is installed by this change. Logs contain only status/owned archive filename, never tokens or payloads. Monitor source `/var/tmp` for leftover ciphertext after failed transfers; cleanup requires identifying that failed run's exact file.

## Restore runbook

1. Select ciphertext by timestamp and copy it to a private offline recovery directory. Keep the original ciphertext. Obtain the offline restore key and certificate; verify fingerprint.
2. Run `python3 restore.py --archive BACKUP.cms --certificate recipient.crt --key restore.key --output recovered.tar`. Enter the key passphrase when prompted. The helper publishes plaintext only after GCM authentication succeeds and refuses to overwrite an existing output. A failed check is a failed restore. `recovered.tar` contains credentials; protect it as strictly as production secrets.
3. Inspect `tar -tf recovered.tar` privately. `manifest.json` maps exact source volume names/paths and records the live-copy consistency limitation. Extract **only into a new empty 0700 staging directory** using GNU tar with numeric ownership, ACLs and xattrs. Do not extract into `/`, the live Docker data root or an existing student volume; do not dereference student symlinks. Do not print manifest/account state into shared logs.
4. On an isolated Docker test host, create new empty volumes and copy each staged `_data` tree into the corresponding new volume while preserving numeric ownership, modes, ACLs and xattrs. Recreate matching labeled containers from the classroom image and manifest mappings; keep ports private and outbound access restricted. Restore manager state into a separate 0700 directory. Service environment, issuer service keys, HTTPS reverse proxy configuration, image artifacts and SSH keys are intentionally **not** included; provision them separately from protected configuration management. Student ID/volume correspondence must remain exact.
5. Verify manager identity mappings, two isolated student workspaces, expected project files and private agent sessions. A restored database/file may need application recovery because this is not a quiesced snapshot. Do not reconnect restored agent credentials to external services during the drill.
6. A production cutover requires a separate reviewed maintenance plan. Never overwrite active volumes or restart students as part of this tool. After recovery rotate exposed/recovered credentials as appropriate and remove plaintext recovery staging according to storage policy.

Tests: `python3 -m unittest discover -s container/classroom/backup -p 'test_*.py'`.
